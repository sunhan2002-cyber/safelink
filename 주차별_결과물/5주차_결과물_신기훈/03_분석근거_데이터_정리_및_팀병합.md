## 2. 결과 화면으로 넘길 분석 근거 데이터 정리

### 2-1. 왜 필요한가

김우영이 이번 라운드에 "결과 화면에서 문장 규칙 근거 / 상황 규칙 근거 / AI 보조분석 근거가
어떻게 보일지" 정리해야 하는데, 지금까지 `DetectionResult`에는 그 셋을 구분할 방법이 없었다.
`matchedKeywords`에는 문장 규칙(`regex-complex`) 매칭이 일반 키워드 매칭과 섞여서 들어가고,
`appliedComboIds`는 콤보 id 문자열만 있어서 어떤 콤보가 "상황 규칙"이고 어떤 게 그냥 "키워드
조합"인지 화면 쪽에서 알 방법이 없었다.

### 2-2. `AnalysisEvidence`

```kotlin
data class AnalysisEvidence(
    val source: String,  // "키워드" | "문장 규칙" | "상황 규칙" | "AI 보조분석"
    val label: String,   // 화면에 바로 쓸 수 있는 짧은 설명
    val detail: String   // 부가 설명 (매칭된 문구, 판정 조건 등)
)
```

`DetectionResult.evidences: List<AnalysisEvidence>` 신설 (기본값 `emptyList()` — 기존
화면/더미데이터 전부 그대로 동작).

### 2-3. 분류 기준

| 데이터 출처 | source |
|---|---|
| `match_type: keyword` / `regex-simple` 매칭 | 키워드 |
| `match_type: regex-complex` 매칭 (예: RS-2-9-003) | 문장 규칙 |
| `combo type: repeat_pattern` / `long_session_pattern` | 상황 규칙 |
| `combo type: numeric_ratio_pattern` | 문장 규칙 |
| `combo type: general` / `specific` (기존 키워드 co-occurrence 콤보) | 키워드 |
| `mergeAiResponse()`로 병합된 서버 응답 | AI 보조분석 |

`general`/`specific` 콤보(예: `COMBO-GENERAL-3CAT`, `COMBO-RS-SECRET-MONEY`)를 "키워드"로
분류한 이유: 이 둘은 1주차부터 있던 "여러 키워드가 함께 나타남" 판정이라, 본질적으로는 아직
문장/상황 규칙(4~5주차에 신설된, 숫자 조건이나 세션 반복을 보는 새로운 메커니즘)과는 다른
층이라고 판단했다.

겹침 억제(`suppressed` — 같은 표현이 원본 키워드와 문구변형 regex 양쪽에 중복 매칭되는 경우)
는 점수 계산과 동일하게 근거에서도 제외해서, 화면에 같은 표현이 두 번 뜨는 일이 없게 했다.

### 2-4. AI 근거 병합

`mergeAiResponse()`가 서버 응답을 병합할 때 AI 근거를 온디바이스 근거 뒤에 이어붙인다 —
화면에서 "키워드/문장 규칙/상황 규칙 근거를 먼저 보여주고 AI 보조분석 근거를 마지막에"
순서로 자연스럽게 나열 가능.

### 2-5. 더미데이터

`DetectionResultDummyData`의 검증된 4종(vpCritical/rsWarning/glCaution/safeEmpty)에
`evidences`를 추가했다 — **전부 기존 `matchedKeywords`/`appliedComboIds`에서 그대로
파생한 값**이라 CLAUDE.md "임의로 숫자 바꾸지 말 것" 원칙을 지켰다. 이 4종은 전부 순수
키워드 매칭 시나리오(문장 규칙/상황 규칙/AI 신호가 실제로 발동하지 않는 케이스)라
`SOURCE_KEYWORD`만 등장한다 — 문장 규칙/상황 규칙/AI 근거를 미리보고 싶으면 01번 문서
4장의 검증된 예시 문장("정 그러면 100만원만요", "너 오늘 좀 예민한 거 같아..." 등)을
실제 `DetectionEngine`에 넣어서 확인하면 된다 (억지로 기존 더미 점수를 바꾸면서까지
욱여넣지 않았음).

## 3. shouldEscalateToAI()와 1차 분석 역할 분리 — 재확인

지난주(5주차 01번 문서) 이미 정리를 끝냈고, 이번 라운드 팀 병합 과정에서도 그 분리가
깨지지 않았는지 확인했다. `runAnalysis()`(팀 쪽 신설)가 `repository.analyze()`(1차,
항상 온디바이스) → `repository.shouldEscalateToAI()`(2차 호출 여부 판단, 회색지대/
수동신고/신규subcategory 3개 조건만) → `repository.escalateToAI()`(실제 호출+병합) 순서
그대로 유지됨을 확인.

## 5. 남은 작업

- `evidences`는 아직 어떤 화면에도 실제로 그려지지 않음 — 데이터 구조만 준비된 상태.
  김재겸이 결과 화면에 렌더링하고, 김우영이 `source`별 문구/아이콘을 입히는 작업이 이어져야
  완성됨
- `general`/`specific` 콤보를 "키워드"로 분류한 게 맞는지는 팀 논의 여지 있음 — 다르게
  보고 싶으면 `buildEvidences()`의 `when (rule.type)` 분기만 바꾸면 됨
