## 2. 결과 화면으로 넘길 분석 근거 데이터 정리

### 2-1. 왜 필요한가

김우영이 이번 라운드에 "결과 화면에서 문장 규칙 근거 / 상황 규칙 근거 / AI 보조분석 근거가
어떻게 보일지" 정리해야 하는데, 지금까지 `DetectionResult`에는 그 셋을 구분할 방법이 없었다.
`matchedKeywords`에는 문장 규칙(`regex-complex`) 매칭이 일반 키워드 매칭과 섞여서 들어가고,
`appliedComboIds`는 콤보 id 문자열만 있어서 어떤 콤보가 "상황 규칙"이고 어떤 게 그냥 "키워드
조합"인지 화면 쪽에서 알 방법이 없었다.

### 2-2. `AnalysisEvidence` (최종본)

```kotlin
data class AnalysisEvidence(
    val label: String,   // 화면에 바로 쓸 수 있는 짧은 설명
    val detail: String   // 부가 설명 (매칭된 문구, 판정 조건 등)
)
```

`source` 태그가 없다 — 어떤 근거인지는 **담기는 필드 자체**가 알려준다:

```kotlin
data class DetectionResult(
    ...
    val matchedKeywords: List<MatchedKeyword>,              // 키워드 근거 (기존 필드 재사용)
    val aiSummary: String?,                                 // AI 근거 (기존 필드 재사용)
    val aiDetectedPattern: String?,                          // AI 근거 (기존 필드 재사용)
    val sentenceRuleEvidences: List<AnalysisEvidence> = emptyList(),     // 문장 규칙 근거 (신설)
    val situationalRuleEvidences: List<AnalysisEvidence> = emptyList()  // 상황 규칙 근거 (신설)
)
```

김우영/김재겸 입장에서는 `result.sentenceRuleEvidences`만 읽으면 바로 문장 규칙 근거 목록,
`result.situationalRuleEvidences`만 읽으면 바로 상황 규칙 근거 목록 — 필터링 코드가 화면
쪽에 전혀 필요 없다.

### 2-3. 분류 기준

| 데이터 출처 | 담기는 필드 |
|---|---|
| `match_type: keyword` / `regex-simple` 매칭 | `matchedKeywords` (기존, 안 바뀜) |
| `match_type: regex-complex` 매칭 (예: RS-2-9-003) | `sentenceRuleEvidences` |
| `combo type: numeric_ratio_pattern` | `sentenceRuleEvidences` |
| `combo type: repeat_pattern` / `long_session_pattern` | `situationalRuleEvidences` |
| `combo type: general` / `specific` (기존 키워드 co-occurrence 콤보) | 별도 근거 텍스트 생성 안 함 — `matchedKeywords`+`appliedComboIds`가 이미 그 근거 |
| `mergeAiResponse()`로 병합된 서버 응답 | `aiSummary`/`aiDetectedPattern` (기존, 안 바뀜) |

`general`/`specific` 콤보는 이번엔 별도 근거 텍스트를 안 만든다 — "이 콤보가 키워드
co-occurrence"라는 사실 자체는 `matchedKeywords`(무엇이 매칭됐는지) + `appliedComboIds`
(어떤 콤보 id가 발동했는지)로 이미 충분히 재구성 가능해서, 굳이 세 번째 표현으로 중복
안 만들었다.

겹침 억제(`suppressed` — 같은 표현이 원본 키워드와 문구변형 regex 양쪽에 중복 매칭되는 경우)
는 점수 계산과 동일하게 `sentenceRuleEvidences`에서도 제외해서, 화면에 같은 표현이 두 번
뜨는 일이 없게 했다.

### 2-4. AI 근거는 새로 안 만듦

`mergeAiResponse()`는 `sentenceRuleEvidences`/`situationalRuleEvidences`를 건드리지
않는다 — AI 근거는 이미 `aiSummary`/`aiDetectedPattern`이라는 전용 필드가 있어서, 세
번째 표현(예: 예전 버전의 `SOURCE_AI` 근거 항목)을 또 만들지 않기로 했다. 화면에서는
"문장 규칙/상황 규칙 근거(온디바이스) → AI 보조분석 근거(aiSummary/aiDetectedPattern,
있을 때만)" 순서로 별도 섹션 두 개를 그리면 된다.

### 2-5. 더미데이터

`DetectionResultDummyData`의 검증된 4종(vpCritical/rsWarning/glCaution/safeEmpty)은
전부 순수 키워드 매칭 시나리오(문장 규칙/상황 규칙 신호가 실제로 발동하지 않는 케이스)라
`sentenceRuleEvidences`/`situationalRuleEvidences`는 기본값 `emptyList()` 그대로 둔다 —
`matchedKeywords`/`appliedComboIds`만으로 이미 정확한 상태라 억지로 채워 넣지 않았다
(CLAUDE.md "임의로 숫자 바꾸지 말 것" 원칙 유지). 문장 규칙/상황 규칙 근거를 미리보고
싶으면 01번 문서 4장의 검증된 예시 문장("정 그러면 100만원만요", "너 오늘 좀 예민한 거
같아..." 등)을 실제 `DetectionEngine`에 넣어서 확인하면 된다.

## 3. shouldEscalateToAI()와 1차 분석 역할 분리 — 재확인

지난주(5주차 01번 문서) 이미 정리를 끝냈고, 이번 라운드 팀 병합 과정에서도 그 분리가

수동신고/신규subcategory 3개 조건만) → `repository.escalateToAI()`(실제 호출+병합) 순서
그대로 유지됨을 확인.

## 5. 남은 작업

- `sentenceRuleEvidences`/`situationalRuleEvidences`는 아직 어떤 화면에도 실제로 그려지지
  않음 — 데이터 구조만 준비된 상태. 김재겸이 결과 화면에 렌더링하고, 김우영이 문구/아이콘을
  입히는 작업이 이어져야 완성됨
- `general`/`specific` 콤보에 별도 근거 텍스트가 없는 게 부족하다고 판단되면(예: "3개 위험
  신호가 함께 감지됨" 같은 문구가 화면에 따로 필요하면), `matchedKeywords`/`appliedComboIds`
  조합 전용 필드를 추가로 만들 수 있음 — 지금은 범위 밖으로 남겨둠

## 6. 개정 배경 (source 태그 방식 → 전용 필드 2개로 재구조화)

최초 버전은 `AnalysisEvidence`에 `source: String`(키워드/문장 규칙/상황 규칙/AI 4종) 태그를
넣고, `DetectionResult`에 `evidences: List<AnalysisEvidence>` 단일 리스트 하나만 뒀다.
동작은 했지만, 리뷰에서 "문장 규칙 근거 / 상황 규칙 근거 기준으로 더 직접 분리해달라 —
지금은 데이터가 존재하긴 해도 각각 따로 표시하기 위한 전용 구조로는 약하다"는 지적을 받았다.

맞는 지적이었다 — 단일 리스트 + 태그 방식은 화면 쪽에서 `evidences.filter { it.source ==
"문장 규칙" }` 처럼 매번 필터링해야 했고, 태그 문자열을 잘못 비교하면(오타 등) 조용히
빈 리스트가 나오는 실수 여지도 있었다. 그래서:

1. `AnalysisEvidence`에서 `source` 필드를 뺐다 (label/detail만 남음)
2. `DetectionResult`에 `sentenceRuleEvidences`/`situationalRuleEvidences` 2개 필드를
   직접 뒀다 — 필터링 없이 바로 꺼내 쓰면 됨
3. 키워드 근거(`matchedKeywords`)와 AI 근거(`aiSummary`/`aiDetectedPattern`)는 이미 전용
   필드가 있었으니 그대로 재사용 — 문장 규칙/상황 규칙만 새로 분리하면 충분했음
4. `mergeAiResponse()`에서 AI 근거를 별도 리스트에 추가하던 코드도 제거 — 이미 있는
   `aiSummary`/`aiDetectedPattern`과 중복이었음

이 변경 시점에 `DetectionResultScreen.kt`(화면 코드) 등 외부 소비자가 아직 없어서
(`git grep`으로 확인) 안전하게 구조를 바꿀 수 있었다. `AnalysisEvidenceTest`도 새 필드
기준으로 다시 작성해서 6개 케이스(키워드만 있으면 둘 다 빈 리스트, 문장 규칙은
`sentenceRuleEvidences`에만, 상황 규칙은 `situationalRuleEvidences`에만, 겹침 억제 반영,
AI 병합 시 두 필드 안 건드림 등)로 검증했다.
