## 3. 규칙 기반 분석의 구조적 한계 (라벨링 데이터 확정본 기준)

`data/신규_기법_문장_수집_v1.json`을 v1.1(확정본)으로 승격했습니다. 38개 문장 전부에
`status`(matched/known_gap)와 `expected_matched_ids`를 채워서 **회귀 테스트 픽스처**로
쓸 수 있게 했고(`TechniqueLabelCorpusTest.kt`), 남은 8건(21%)은 원인별로 분류했습니다.

| 원인 분류 | 건수 | 의미 | 개선 방향 |
|---|---|---|---|
| PARAPHRASE(패러프레이즈) | 5 | 같은 뜻, 다른 표현 | 키워드 계속 추가하면 점근적으로 개선 가능 |
| NUMERIC_PATTERN(숫자+단위 패턴) | 1 | "100만원만요" 같은 숫자+조사 조합 | regex로 개선 가능(이번엔 의도적으로 보류) |
| NUMERIC_REASONING(숫자 관계 추론) | 1 | "100이 137 됐죠?" = 수익률 37% 이해 필요 | **키워드 매칭으로 구조적으로 거의 불가능** |
| TONE_IMPLICATURE(어조·함의 의존) | 1 | 문자 그대로는 안전, 맥락상 위험 | **키워드 매칭 구조적 한계 — AI가 필요한 대표 사례** |

**결론**: PARAPHRASE·NUMERIC_PATTERN은 "아직 안 채운 것"이라 규칙 엔진을 계속 키우면
줄어들지만, NUMERIC_REASONING·TONE_IMPLICATURE는 **규칙 기반 키워드 매칭이라는 방법론
자체의 한계**입니다. 이게 AI 보조 분석이 왜 필요한지의 핵심 근거입니다.

## 4. AI API 진입 조건 확정본

`data/API 입출력 초안 v1`의 기존 조건(회색지대, 가스라이팅 반복 예외)에 05번 문서에서
제안했던 4개를 검토해서 **최종 5개 조건**으로 확정합니다. (이 문서에서 확정한 것이고,
`API 입출력 초안 v1` 파일 자체는 여러 사람이 참조하는 공식 문서라 직접 고치지 않았습니다
— 팀 검토 후 그 문서에 반영 필요.)

| # | 조건 | 근거 |
|---|---|---|
| 1 | 온디바이스 누적점수가 20~40 또는 55~70 (회색지대) | 기존 유지 |
| 2 | 가스라이팅 `3-1·3-2·3-7·3-8·3-9` 중 2회 이상 감지 시 점수 무관 호출 | 기존 3-1/3-2에 4주차 신설 3건(BLAME_SHIFT/DISCREDIT/INTERMIT) 추가 — 전부 3장의 TONE_IMPLICATURE 유형이라 동일 취급 |
| 3 | 로맨스스캠 `2-8`(FUTURE_FAKE) 또는 `2-10`(SUNK_COST) 감지 + 세션 15턴 이상 | 이 두 기법은 단일 문장이 아니라 장기 서사 흐름에서만 의미가 있음(3장 NUMERIC_REASONING/맥락의존 사례와 같은 이유) |
| 4 | 사용자가 수동으로 "위험한 것 같다" 표시 | 21% 갭이 구조적 한계라는 근거(3장) — 사용자 판단으로 보완 |
| 5 | *(한시적)* 4주차 신설 중분류(`2-6~2-10, 3-7~3-9`) 매칭 시 점수 무관 호출, `newSubcategoryRolloutActive` 스위치로 관리 | 아직 시나리오 6건 기반 설계라 실사용 검증 전까지 더 자주 AI 확인받도록. 실측 데이터 쌓이면 스위치 꺼서 해제 |

기존 제외 조건(20점 미만·70점 이상은 원칙적으로 호출 안 함, 시간당 20회 제한)은 그대로
유지합니다.

## 5. 김재겸이 바로 붙일 인터페이스

`DetectionRepository`에 함수 2개면 끝입니다.

```kotlin
// 1. 온디바이스 분석 (이미 연동되어 있음, 02번 문서)
val result: DetectionResult = detectionRepository.analyze(originalText)

// 2. AI 보조 분석 필요 여부 판단 (이번에 추가됨)
val needsAI: Boolean = detectionRepository.shouldEscalateToAI(
    result = result,
    sessionTurnCount = /* 지금까지 세션 누적 턴 수 */,
    manualReportFlag = /* 사용자가 "위험한 것 같다" 눌렀는지 */ false
    // newSubcategoryRolloutActive는 기본값 true — 백엔드 실측 데이터 쌓이면 false로 전환
)

if (needsAI) {
    // TODO(백엔드 미구현): masked_text 등으로 /analyze 호출 -> context_score_adjustment 받아서
    // result.score에 반영. data/API 입출력 초안 v1 스키마 그대로 사용.
}
```

`shouldEscalateToAI()`는 4장의 5개 조건을 그대로 코드화한 것이라, **"언제 불러야 하는지"는
이미 정해져 있고 실제 네트워크 호출만 얹으면 됩니다** (백엔드 자체가 아직 없어서 호출부는
TODO로 남겨둠).
