## 2. 입력 텍스트 분석 기준

진입점은 하나다.

```kotlin
DetectionRepository.analyze(originalText: String): DetectionResult
```

내부적으로는 `analyze(turns: List<String>)`로 동작한다 (`originalText` 하나만 넘기면
`listOf(originalText)`로 처리). 멀티턴 리스트를 받는 이유는 `keyword.json`의 콤보 조건
(예: "최근 10턴 이내 동시 감지")과 `data/위험 문장 테스트.json`의 경계/콤보 케이스가 여러
턴에 걸친 대화를 기준으로 정의돼 있어서, 같은 로직으로 검증 가능하게 하기 위함이다.
이번 주 앱 쪽 실제 사용은 `analyze(originalText)` 한 줄이면 충분하다.

## 3. 키워드 매칭 구조

`keyword.json`의 `match_type` 필드를 그대로 따른다.

| match_type | 매칭 방식 |
|---|---|
| `keyword` | 원문에서 `keyword` 값과 완전히 일치하는 부분 문자열을 전부 찾음 (`indexOf` 반복 탐색) |
| `regex-simple` | `pattern` 정규식으로 `Regex.findAll` |

`structural_only: true`(전화번호 `VP-1-3-003`, URL `VP-1-6-004`)는 매칭은 기록하되 **점수에는
포함하지 않는다** — 콤보 트리거 전용.

매칭 하나마다 `MatchedKeyword`로 변환:

```kotlin
MatchedKeyword(
    keywordId = "VP-1-1-001",       // keyword.json의 id
    subcategoryId = "1-1",
    subcategoryName = "기관사칭",     // 결과 화면 태그로 노출
    matchedText = "택배기사",         // 원문에서 실제로 매칭된 문자열
    startIndex = 0, endIndex = 4,    // originalText 기준 위치 (밑줄 강조용, Task 6.10 TODO에 대응)
    weight = 15,
    description = "택배기사 사칭 접근"
)
```

## 4. 점수 계산 방식 (v1)

1. **반복감쇠**: `keyword.json`의 `repeat_decay_policy` 그대로 — 같은 `subcategory_id` 안에서
   위치 순으로 1번째 매칭은 100%, 2번째부터는 50%. `repeat_decay: false`인 항목(전화번호/URL)은
   감쇠 대상에서 제외(항상 100%, 어차피 weight 0).
2. **콤보 보너스**: `combo_bonus_rules` 6개 중
   - `COMBO-GENERAL-3CAT`/`4CAT`(서로 배타, 더 높은 것만 적용): 매칭된 서로 다른 `subcategory_id`
     개수로 판정
   - 나머지 4개(`COMBO-VP-PHONE-VERIFY`, `COMBO-VP-SMISHING`, `COMBO-RS-SECRET-MONEY`,
     `COMBO-GL-ISOLATION-GUILT`)는 트리거 조건이 서로 달라 조건문을 각각 코드화함
     (일반화된 규칙 엔진이 아니라 지금 있는 6개 기준 v1 초안 — 9장 "남은 작업" 참고)
3. **합산**: `base + combo`, 100점 캡, `Int`로 버림 처리(`82.5 → 82`, 기존 더미데이터
   `vpCritical=82`/`rsWarning=47`과 동일한 버림 규칙).

## 6. 추천 기관이 붙는 조건

`data/API 입출력 초안 v1` 3-1장 resolve 흐름을 그대로 구현:

```
매칭된 subcategory_id
  → standalone_recommend 게이팅
     - true: 항상 포함
     - false(1-3/2-1/2-2/3-1/3-2/3-4 총 6개): 이 subcategory가 트리거된 콤보의 일부이거나,
       세션 누적 점수가 31점(중간) 이상일 때만 포함
  → institutions.json의 subcategory_to_risk_type 조회 (+ keyword_risk_type_additions로
    특정 키워드에만 위험유형 추가, 예: "찾아갈 거야" → 스토킹위협)
  → risk_type_priority 조회
  → institution_id 기준 dedup(첫 등장만 유지) 후 최종 배열 인덱스로 rank 1부터 재부여
```

**설계 결정 사항 (문서에 근거가 명확하지 않아 직접 정한 부분)**:
- 위험유형 노출 순서: 그 위험유형을 만든 subcategory 중 **weight가 가장 높은 것** 기준
  내림차순. 동률이면 먼저 매칭된 subcategory 순서 유지.
- 이 부분은 API 문서에도 "관련성 높은 위험유형을 먼저 배치"라고만 돼 있어 해석의 여지가
  있음 — 팀 검토 시 다른 기준이 낫다고 판단되면 바꿀 수 있음.

## 7. `DetectionResult`에 들어가는 최종 값

기존 `DetectionResult.kt`/`MatchedKeyword`/`RecommendedInstitutionUi` 구조를 **그대로** 채운다
(필드 추가/변경 없음 — `김선한_03_입력값_결과값_용어_통일본.md`의 용어와도 전부 일치 확인함).

```kotlin
DetectionResult(
    riskLevel = RiskLevel.fromScore(score),
    score = score,
    category = "보이스피싱" | "로맨스스캠" | "가스라이팅" | "",   // 매칭 없으면 ""
    originalText = originalText,
    matchedKeywords = listOf(...),
    recommendedInstitutions = listOf(...),   // 게이팅 통과 없으면 emptyList()
    appliedComboIds = listOf(...)
)
```

매칭이 0건이면 `score=0`, `category=""`, 나머지 다 빈 리스트 → `isSafeAndEmpty=true`.
기존 `DetectionResultDummyData.safeEmpty`와 동일한 패턴.

## 9. 발견된 이슈 / 남은 작업

### 9-1. 결론부터: 엔진 로직 기준 문제 없음

보류된 3건은 전부 `DetectionEngine`의 계산 로직(반복감쇠/콤보/게이팅) 버그가 아니라,
`keyword.json`의 `match_type: keyword`(완전 부분일치) 규칙을 있는 그대로 실행한 결과다.
즉 **"코드가 틀려서" 난 문제가 아니라 "원본 데이터에 이런 케이스가 있는 줄 몰랐던" 문제**다.

### 9-2. keyword.json / 테스트 픽스처 수정 논의 필요 (팀 논의 필요, 코드로 임의 수정하지 않음)

1. **키워드 부분 문자열 충돌** (`keyword.json` 수정 논의 대상): `VP-1-4-003`("오늘 안에",
   보이스피싱, weight20)이 `RS-2-5-001`("오늘 안에 처리 안되면", 로맨스스캠, weight20)의
   부분 문자열이다. 두 항목이 서로 다른 subcategory(1-4/2-5)라 반복감쇠가 안 걸리고
   20+20=40으로 계산됨. `TC-RS-POS-05`, `TC-RS-NEG-04`가 이 이유로 보류됨.
   `weight`/`keyword` 문구 조정이나 "다른 카테고리 매칭 시 우선순위" 같은 규칙 추가가
   필요한지는 신기훈/김선한 논의 필요.
2. **테스트 픽스처 자체 불일치** (`위험 문장 테스트.json` 수정 논의 대상): `TC-RS-NEG-02`의
   `expected_matched_ids`에 `RS-2-2-003`("결혼하고 싶어요")이 포함돼 있는데, 실제 입력 문장은
   "우리 결혼할까?"라서 부분일치 규칙으로는 매칭되지 않음. 픽스처 쪽 오기로 보임 — 확인 후
   픽스처 수정이 필요할 수 있음.

**남은 작업**

- 김재겸: `DetectionViewModel`에서 `DetectionRepository.analyze(originalText)` 호출 →
  `DetectionResultScreen`에 실제 결과 바인딩 (Task 6.10 TODO 대체)
- 이 저장소에 Android SDK가 없어 `./gradlew test`/`assembleDebug` 실측을 못 했음 — 로컬
  개발 환경에서 한 번 더 돌려서 확인 필요
- 위 이슈 1, 2 팀 논의 후 처리 (keyword.json 수정이 필요하면 CLAUDE.md 작업 원칙 3번대로
  `id`/`weight`/`repeat_decay`/`match_type` 스키마 지키면서 진행)
- `evaluateComboRules`의 4개 specific 콤보는 지금 데이터셋 6개 규칙 기준으로 하드코딩됨 —
  콤보 규칙이 더 늘어나면 일반화된 조건 파서로 리팩터링 필요 (지금은 v1 초안 범위 밖으로 보류)
- `originalText`를 서버로 보낼 때의 마스킹(`[전화번호]`/`[링크]`)은 이번 주 범위 밖 (서버
  연동은 회색지대 점수일 때만 필요하며 Task 6.x 이후 범위)

## 10. 김재겸 연동용 최소 호출 예시

`DetectionInputScreen`에서 받은 원문 텍스트 하나로 결과를 만들 때, 필요한 건 이 한 줄뿐이다.

```kotlin
val result = detectionRepository.analyze(originalText)
// result: DetectionResult — DetectionResultScreen이 이미 쓰고 있는 구조 그대로
```
