# 신기훈 4주차 결과물 09 - 반복/세션 패턴을 1차 위험도 계산에 반영

> "신기훈 4주차 결과물 수정 2" 리뷰 대응. 핵심 지적: *"문장/상황 기반 분석이 1차 위험도
> 계산 로직 본체에 들어가 있지 않다 — `DetectionEngine.analyze()`는 여전히 키워드매칭/
> repeat_decay/combo_bonus 중심이고, 가스라이팅 반복·장기세션·신규subcategory·수동신고
> 같은 상황 기반 조건은 `shouldEscalateToAI()`에서 AI 호출 여부 판단에만 쓰인다."*

---

## 1. 지적 사실관계 확인

리뷰 지적은 정확했다. [DetectionEngine.kt](../../android/app/src/main/java/com/safelink/app/data/repository/DetectionEngine.kt)의
`analyze()`(1차 위험도 계산 본체)는 키워드 매칭 → 겹침 억제 → `repeat_decay` → `combo_bonus_rules`
로만 점수를 계산했고, `shouldEscalateToAI()`의 4개 조건(가스라이팅 반복 2회+, 장기세션 15턴+,
신규 subcategory, 수동 신고)은 전부 "AI를 부를지"에만 쓰이고 점수에는 전혀 반영되지 않았다.

## 2. 그런데 이걸 그대로 고치면 CLAUDE.md 원칙을 어긴다

CLAUDE.md 아키텍처 원칙 1(절대 위반 금지): *"위험도 계산은 항상 온디바이스... 서버가 최종
위험도를 결정하면 원칙 위반."* AI가 1차 점수 계산에 직접 관여하는 방향으로 고치면 이 원칙을
정면으로 어기게 된다. 그래서 **AI 없이, 온디바이스 규칙만으로** 반복/세션 패턴 신호를 점수에
반영하는 방향으로 대응했다 — `shouldEscalateToAI()`가 "부를지 말지"만 판단하는 구조 자체는
그대로 두고, `analyze()`의 콤보 보너스 체계에 새 규칙 타입 2개를 추가했다.

수동 신고(`manualReportFlag`)와 신규 subcategory 게이팅(`newSubcategoryRolloutActive`)은
"텍스트에서 감지된 패턴"이 아니라 각각 "사용자 입력값"·"데이터 신뢰도 임시 스위치"라서 온디바이스
점수 반영 대상에서 제외했다 — 아래 3장 참고.

## 3. 무엇을 반영하고 무엇을 안 했는지

| shouldEscalateToAI 조건 | 1차 점수 반영 여부 | 이유 |
|---|---|---|
| 가스라이팅 반복 2회+ (3-1/3-2/3-7/3-8/3-9) | ✅ 반영 (`COMBO-GL-REPEAT-PATTERN`, +15) | 텍스트에서 실제로 감지되는 반복 패턴 — 온디바이스 규칙만으로 판정 가능 |
| 장기세션 15턴+ (2-8/2-10) | ✅ 반영 (`COMBO-RS-LONG-SESSION-PATTERN`, +15) | 마찬가지로 온디바이스에서 턴 수만 세면 판정 가능 |
| 신규 subcategory(2026-07 추가분) | ❌ 미반영 | "이 패턴이 위험하다"가 아니라 "이 키워드들의 weight가 아직 실사용 검증 전이라 못 미덥다"는 신뢰도 문제 — 점수를 더 주는 게 아니라 AI로 한 번 더 확인하자는 게 원래 의도 |
| 수동 신고 | ❌ 미반영 | 텍스트 분석 결과가 아니라 사용자가 직접 누른 값 — "감지된 위험 패턴"으로 취급하면 사용자 입력이 곧 점수가 되는 이상한 구조가 됨 |

## 4. 구현

`data/keyword.json`의 `combo_bonus_rules`에 새 타입 2개 추가 (스키마: `subcategory_ids`는
**any-of** — 기존 `related_subcategory_ids`의 all-of와 의미가 다름):

```json
{ "id": "COMBO-GL-REPEAT-PATTERN", "type": "repeat_pattern",
  "subcategory_ids": ["3-1","3-2","3-7","3-8","3-9"], "min_match_count": 2, "bonus": 15 }
{ "id": "COMBO-RS-LONG-SESSION-PATTERN", "type": "long_session_pattern",
  "subcategory_ids": ["2-8","2-10"], "min_turns": 15, "bonus": 15 }
```

`DetectionEngine.evaluateComboRules()`에서 처리:
- `repeat_pattern`: `subcategory_ids` 중 하나라도 해당하는 매칭이 세션 전체에서 `min_match_count`
  이상이면 발동
- `long_session_pattern`: `subcategory_ids` 매칭이 하나라도 있고 `turnCount >= min_turns`이면 발동

`shouldEscalateToAI()`의 기존 임계값(가스라이팅 2회, 세션 15턴)과 **의도적으로 같은 값을 병행
유지**한다 — "AI를 부를지"와 "온디바이스 점수에 얼마나 더할지"는 서로 다른 관심사라 별도
상수/필드로 존재하지만, 같은 패턴을 가리키므로 한쪽을 바꾸면 다른 쪽도 검토해야 한다는 주석을
양쪽에 남겨뒀다([DetectionEngine.kt:390](../../android/app/src/main/java/com/safelink/app/data/repository/DetectionEngine.kt:390) 근처).

## 5. 겹침 억제와의 상호작용 (구현 중 실제로 잡은 버그)

구현하고 41개 케이스로 재검증하는 과정에서 실제 버그를 하나 잡았다. `TC-GL-POS-02`
("내가 언제 그렇게 말했어? 기억이나 하고 말하는 거야?")가 기존 12점에서 27점으로 튀는
회귀가 발생했는데, 원인은 `GL-3-2-001`(원문 그대로)과 `GL-3-2-006`(문구 변형 대응
regex, 4주차 신설)이 **같은 구간의 같은 표현을 중복 매칭**하고 있었기 때문이다
(`findSuppressedByOverlap`가 점수 계산에서는 이미 이 중복을 걸러내는데, 새로 만든
`repeat_pattern` 카운트는 억제되지 않은 raw match를 그대로 세고 있었음).

`같은 표현이 두 keyword id로 중복 매칭된 것`과 `실제로 서로 다른 두 표현이 반복된 것`은
구분해야 하므로, `repeat_pattern`/`long_session_pattern` 판정도 겹침 억제(`suppressed`) 이후의
매칭만 대상으로 세도록 수정했다 (`scoreMatches`와 동일한 `suppressed` 집합을 공유).

## 7. 여전히 남아있는 한계

- `long_session_pattern`은 실사용에서는 사실상 미발동한다 — `DetectionViewModel`이 아직
  단일 입력(turns=1) 기준이라서다 (07번 문서 "recentTurns 한계" 참고). 다중 턴 세션 추적이
  생기면 자동으로 활성화됨 — 이 콤보 규칙 자체는 이미 준비돼 있음.
- 신규 subcategory 신뢰도 문제(3장 표)와 수동 신고는 이번에도 여전히 AI 호출 판단에만
  쓰인다 — 이건 애초에 "온디바이스 점수에 반영할 성격의 신호"가 아니라고 판단해서 의도적으로
  범위 밖에 뒀다. 팀이 다른 의견이면 논의 필요.
