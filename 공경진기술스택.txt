Safelink 공학경진대회 기술스택

작성 기준
- 기존 Safelink 로드맵과 세부일정을 반영함
- 시험기간 이후 2026.06.16 ~ 2026.08.28 안에 구현 가능한 방향으로 선정
- 핵심 기능은 위험 감지, 지원 매칭, 신청 동행, 배너 알림 시연임
- 팀원들이 대학 과정에서 이미 접한 언어를 우선 사용해 협업 효율을 높이는 방향으로 구성함
- AI와의 협업을 통해 개발 생산성을 높인다는 프로젝트 방향을 반영함

전체 기술 방향
- 앱 화면과 안드로이드 기능은 Java 기반으로 구현
- 위험 문장 분석과 추천 로직은 Python 기반으로 구현
- 프론트엔드와 백엔드를 분리해 역할을 명확히 나눔
- 실제 상용 서비스 수준의 복잡한 구조보다 공학경진대회 데모와 발표에 적합한 구조를 우선함
- 백그라운드 감지 기능은 실제 메신저 완전 연동보다 시연 가능한 권한 기반 또는 데모 기반 구조로 설계함

1. 전체 기술스택

앱 프론트엔드
- Java
- Android Studio
- XML 레이아웃
- 이유: 대학 과정에서 익숙한 안드로이드 개발 환경을 활용할 수 있고, 배너 알림과 백그라운드 서비스 시연에 유리함

백엔드
- Python
- FastAPI 또는 Flask
- 이유: 위험 문장 분석, 추천 로직, 간단한 API 서버 구현에 적합하고 AI 협업과의 연결성이 좋음

데이터 저장
- MySQL 또는 SQLite
- 안드로이드 로컬 저장은 SharedPreferences 또는 Room
- 이유: 사용자 기록, 위험 체크 결과, 기관 정보 저장 구조를 단순하게 관리할 수 있음

보안
- 앱 잠금 비밀번호
- 안드로이드 생체인증 API
- 로컬 데이터 암호화
- 이유: 가정폭력 등 민감한 상황에서 앱 접근 자체를 보호해야 하기 때문임

서버 연동
- REST API
- JSON 데이터 통신
- 이유: Java 안드로이드 앱과 Python 서버를 연결하기 가장 단순하고 안정적인 방식임

알림
- Android Notification
- Foreground Service
- 이유: 백그라운드 실행 중 위험 신호 감지와 배너 알림 시연에 적합함

AI 또는 분석 로직
- Python 기반 키워드 탐지
- Python 기반 규칙 분류
- 필요 시 scikit-learn 기반 경량 텍스트 분류
- 이유: 짧은 일정 안에 구현 가능한 수준에서 위험 문장 탐지 데모를 만들기 좋음

협업 및 문서화
- GitHub
- Notion 또는 Google Docs
- Figma
- 이유: AI와 협업한 개발 기록, 기획 문서, 화면 설계를 함께 관리하기 좋음

2. 백엔드

백엔드 목표
- 위험 대화 분석 처리
- 위험도 분류 결과 반환
- 사용자 상황에 맞는 지원 제도 추천
- 위험 기록 저장 및 조회 지원

추천 구성
- Python
- FastAPI 또는 Flask
- 역할: 앱으로부터 텍스트 또는 체크 결과를 받아 분석 결과를 반환

- 분석 로직
- 역할: 위험 문장 키워드 탐지, 반복 통제 표현 판단, 위험 단계 분류

- 데이터베이스
- 역할: 상담 기관 정보, 복지 제도 정보, 위험 기록, 사용자 저장 메모 관리

백엔드에서 다룰 데이터
- 위험 체크리스트 응답
- 대화 분석 요청 텍스트 또는 데모 입력값
- 위험 단계 결과
- 추천 상담 기관 및 지원 제도
- 사용자가 저장한 상황 메모
- 긴급 연락 또는 빠른 연결 정보

백엔드 구현 우선순위
1. 위험 체크 결과를 받아 위험 단계를 반환하는 API 구현
2. 상담 기관 및 복지 제도 추천 API 구현
3. 기록 저장 및 조회 API 구현
4. 필요 시 위험 문장 탐지 로직 고도화

백엔드 세부 기술 후보
- Python 3
- FastAPI 또는 Flask
- Uvicorn
- SQLAlchemy
- MySQL 또는 SQLite
- pandas는 데이터 정리에만 선택적으로 사용
- scikit-learn은 시간이 될 경우 경량 모델 적용에 사용

백엔드 주의사항
- 민감한 원문 대화는 장기 저장하지 않는 방향이 바람직함
- 대회 시연용은 정확도보다 흐름 완성과 설명 가능성이 중요함
- 실제 기관 자동 신청보다 추천과 연결 안내 중심으로 구현하는 것이 일정상 현실적임

3. 프론트엔드

프론트엔드 목표
- 사용자가 위험 신호를 빠르게 확인할 수 있어야 함
- 감지에서 지원 연결까지 흐름이 자연스럽게 이어져야 함
- 발표 시연에서 기능 가치가 한눈에 보여야 함

추천 구성
- Java
- Android Studio
- XML 기반 UI
- Retrofit 또는 Volley
- Room 또는 SharedPreferences

프론트엔드 핵심 기능
- 체크리스트 입력
- 위험 분석 요청 및 결과 수신
- 위험도별 결과 화면 표시
- 지원 제도 및 상담 기관 추천 화면 제공
- 신청 동행 안내 화면 제공
- 긴급 도움 요청 화면 제공
- 배너 알림 클릭 시 대응 가이드 이동
- 비밀번호 또는 생체인증 기반 앱 잠금
- 민감 화면 진입 시 재인증

주요 화면
- 시작 화면
- 로그인 또는 간단 사용자 진입 화면
- 메인 대시보드
- 위험 체크리스트 화면
- 위험 감지 결과 화면
- 지원 기관 추천 화면
- 복지 제도 안내 화면
- 신청 동행 안내 화면
- 상황 기록 화면
- 긴급 도움 요청 화면
- 배너 알림에서 진입하는 대응 가이드 화면

프론트엔드 구현 우선순위
1. 메인 화면과 위험 체크리스트 구현
2. 결과 화면과 추천 화면 구현
3. 백그라운드 감지 데모와 배너 알림 구현
4. 기록 저장 및 긴급 대응 화면 구현

프론트엔드 세부 기술 후보
- Java
- Android SDK
- XML Layout
- RecyclerView
- Retrofit
- Gson
- Room
- SharedPreferences
- NotificationManager
- Foreground Service
- BiometricPrompt
- EncryptedSharedPreferences

프론트엔드 주의사항
- 카카오톡 직접 연동은 정책과 기술 제약이 있을 수 있으므로 발표용 데모 구조로 먼저 구현
- 실제 메신저 수집보다 알림 접근 권한, 복사 텍스트 분석, 데모 채팅 데이터 방식이 더 현실적임
- 7월 안에는 전체 흐름이 보이는 수준까지 구현하는 것이 중요함
- 알림 문구는 앱 존재나 위험 상황을 직접 노출하지 않도록 중립적으로 설계하는 것이 바람직함

4. UI/UX

UI/UX 목표
- 위험한 상황에서도 사용자가 빠르게 이해하고 행동할 수 있어야 함
- 경고는 분명하지만 과도하게 공포감을 주지 않아야 함
- 도움 요청까지 이어지는 버튼과 흐름이 직관적이어야 함

UI 방향
- 신뢰감과 안정감을 주는 블루 계열을 기본색으로 사용
- 위험도는 노랑, 주황, 빨강으로 단계 구분
- 정보는 카드형 레이아웃으로 정리
- 첫 화면에서 현재 상태 확인과 빠른 도움 요청이 가능하도록 구성

UX 핵심 원칙
- 위험 감지 후 1~2번의 선택으로 대응 가이드에 진입 가능
- 도움 요청 버튼은 항상 눈에 잘 띄는 위치에 배치
- 긴 설명보다 짧은 안내 문구 중심으로 설계
- 위험 수준별로 행동 버튼을 다르게 제공
- 앱 실행 시 빠르고 안전한 본인 인증이 가능해야 함
- 타인이 화면을 보더라도 민감 정보가 바로 드러나지 않도록 해야 함

중요 UX 포인트
- 배너 알림 문구 예시
- 주의: 불편한 대화 신호가 감지되었어요
- 경고: 반복적 통제 표현이 감지되었어요
- 긴급: 지금 바로 도움을 요청할 수 있어요

- 행동 버튼 예시
- 대응 가이드 보기
- 상담 기관 연결
- 지원 제도 확인
- 기록 남기기
- 긴급 연락하기

UI/UX 구성 요소
- 위험 단계 배지
- 체크 결과 요약 카드
- 추천 기관 카드
- 빠른 행동 버튼
- 최근 감지 기록 리스트
- 배너 클릭 후 대응 안내 팝업 또는 전환 화면
- 잠금 해제 화면
- 생체인증 안내 팝업
- 민감 정보 보호용 가림 화면

UI/UX 구현 우선순위
1. 메인 대시보드와 위험 결과 화면 디자인
2. 배너 알림과 대응 가이드 흐름 정리
3. 기관 추천과 신청 동행 화면 정리
4. 발표용 시연 시나리오에 맞춘 화면 연결 보완

5. 대회용 최종 추천 조합

가장 현실적인 조합
- 프론트엔드: Java + Android Studio + XML
- 백엔드: Python + FastAPI 또는 Flask
- 데이터 저장: MySQL 또는 SQLite + Room
- 통신: REST API + JSON
- 알림: Android Notification + Foreground Service
- 보안: BiometricPrompt + EncryptedSharedPreferences
- 협업: GitHub + Notion + Figma

이 조합을 추천하는 이유
- 팀원들이 배운 언어 기반으로 개발할 수 있어 진입장벽이 낮음
- AI와 협업할 때 Java와 Python은 예시와 자료가 많아 도움을 받기 쉬움
- Java는 안드로이드 기능 시연에 강하고 Python은 분석 로직 구현에 강함
- 기능 기준 역할 구조를 잡기 쉬워 짧은 일정에도 병렬 작업이 가능함
- 발표에서 기술 선택 이유를 설명하기 좋음

6. 역할 구조 참고

- 역할 분담은 언어 기준이 아니라 기능 기준으로 구성한다.
- 최종 역할 구조는 `기획 / 스펙 설계 / 문서화`, `위험 감지 / 백엔드`, `프론트엔드 / UIUX`, `지원 연결 / 사용자 보호 기능`의 4개 파트로 정리한다.
- 발표 자료와 제출물은 특정 한 파트가 아니라 팀 전체 공동 작업으로 진행한다.

7. 발표에서 강조할 기술 포인트
- 대학 과정에서 익힌 Java와 Python을 기반으로 현실적인 개발 구조를 구성했다는 점
- AI와 협업하여 앱 개발과 위험 분석 로직을 빠르게 구현했다는 점
- 위험 신호 감지에서 지원 연결까지 이어지는 통합 흐름을 설계했다는 점
- 백그라운드 감지와 배너 알림을 통해 즉시 대응을 유도한다는 점
- 짧은 개발 기간 안에서도 구현 가능한 기술 조합으로 실현 가능성을 높였다는 점
