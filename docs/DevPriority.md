## 우선순위 판단 기준

1. **의존성** — 다른 화면·기능의 선행 조건인가 (NavGraph, 홈)
2. **서버 독립성** — FastAPI 백엔드 없이 완성 가능한가 (자가진단·지원 연결은 가능, 대화 분석은 불가)
3. **데모 가치** — 발표 시연의 핵심 경로인가 (대화 분석 > 자가진단 > 지원 연결)
4. **일정** — Tasks.md 스프린트 배정 (오늘 7/11 = Sprint 4 마지막 주말)

> 핵심 결론: **대화 분석이 데모의 핵심이지만 서버(Sprint 6)에 의존하므로, 서버 없이 완성되는 화면부터 조립한다.** 자가진단 흐름은 로컬 로직만으로 완결되므로 가장 먼저 끝낼 수 있는 완전한 기능이다.

## 요약: 다음 주(7/14~7/20) 작업 순서

```
NavGraph/탭 → 홈 → 자가진단 → 진단결과 → 대응가이드   (전반)
→ 지원추천 → 기관상세 → 긴급요청(+설정 최소버전) → 신청안내   (후반)
```

이렇게 하면 다음 주말 기준으로 **여정 B(자가진단)와 여정 C(긴급)가 서버 없이 완전 동작** — 중간 발표나 데모가 잡혀도 보여줄 게 있는 상태가 된다.

## 조정 참고

- **ResponseGuideScreen 앞당김**이 Tasks.md와 다른 유일한 변경 (Sprint 6 → P1). 이유: 진단 결과에서 이동할 곳이 없으면 자가진단 흐름이 막다른 길이 됨. 정적 콘텐츠라 비용도 낮음.
- **SettingsScreen 최소 버전**(긴급 연락처 입력만)을 P2에 포함하면 EmergencyScreen의 지인 문자 기능을 실제로 시연 가능.
- DetectionInputScreen UI는 서버 완성 전에 목 데이터로 개발 시작 가능 — 백엔드 일정이 밀리면 P2 직후로 앞당길 것.
