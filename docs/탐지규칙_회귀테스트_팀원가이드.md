## 0. 왜 팀원 도움이 필요한가

규칙(키워드·패턴)과 테스트 문장을 **같은 사람이 쓰면 점수가 부풀려진다.**
실제로 재겸(+Claude)이 규칙과 문장을 둘 다 썼을 때 결과가 이렇게 갈렸다.

| 측정 문장 | 탐지율 |
|---|---|
| 규칙을 고치면서 본 문장 | 21% → **100%** |
| 규칙을 고칠 때 **보지 않은** 문장 | 6% → **22%** |

규칙을 만든 사람의 말투에 맞춰졌다는 뜻이다.
그래서 **규칙을 보지 않은 사람이 쓴 문장**으로 따로 재야 진짜 정확도가 나온다.

9/16 기준 확인용(holdout) 문장 54개도 **Claude가 쓴 것**(`author: claude-holdout2`)이라 참고치다.

| 확인용 문장 36개 (위험) | 탐지율 |
|---|---|
| 규칙만 | 25% (9/36) |
| AI 보조분석 포함(실제 API 3회 측정) | 약 61% |

**팀원이 쓴 확인용 문장이 아직 0개**라, 발표에 쓸 숫자는 2장 문장이 들어온 뒤에 다시 잰다.

| 역할 | 누가 | 하는 일 |
|---|---|---|

> 보고 나서 쓰면 규칙에 맞춘 문장이 되어 측정 의미가 없어집니다.

## 2. 확인용 문장 쓰기 (가장 중요)

### 수정할 파일
```
android/app/src/test/resources/rule_regression_cases.json
```
`"cases": [ ... ]` 배열 **맨 끝**에 항목을 추가합니다.

### 몇 개 쓰나
유형 9개 × **위험 2개 + 일상 2개** = 36개 정도 (많을수록 좋음)

| 유형 이름 (정확히 이대로) | id 약어 |
|---|---|
| 보이스피싱 | VP |
| 로맨스스캠 | RS |
| 가스라이팅 | GL |
| 가족사칭 | FM |
| 투자사기 | IV |
| 대출사기 | LN |
| 협박·갈취 | TH |
| 부업사기 | JB |
| 중고거래사기 | UD |

> `협박·갈취`의 가운데 점은 `·`(가운뎃점)입니다. 다르게 쓰면 유형별 집계가 따로 나옵니다.

### 항목 형식
```json
{
  "id": "FM-HD-선한01",
  "category": "가족사칭",
  "kind": "danger",
  "author": "김선한",
  "source": "holdout",
  "text": "엄마 나 폰 떨어뜨려서 수리 맡겼어\n지금 친구 폰이라 통화는 어려워\n급한 결제 있는데 엄마 카드로 먼저 해줄 수 있어?"
}
```

| 필드 | 쓰는 법 |
|---|---|
| `id` | `유형약어-H + D(위험)/B(일상) - 이름+번호`. **다른 항목과 겹치면 안 됨** |
| `category` | 위 표의 유형 이름 그대로 |
| `kind` | 사기·위험 대화면 `"danger"`, 일상 대화면 `"benign"` |
| `author` | 본인 이름 |
| `source` | 확인용이면 반드시 **`"holdout"`** |
| `text` | 대화 내용. 메시지가 여러 개면 **`\n`으로 구분** (한 줄 = 메시지 하나) |

### 좋은 문장 쓰는 법
**위험 대화 (`danger`)**
- 실제 받았던 문자, 뉴스·경찰청 사례처럼 **진짜 사기꾼 말투**로
- 키워드를 떠올리지 말고 **내가 사기꾼이라면 뭐라고 할지** 생각하며 쓰기
- 오타·줄임말·띄어쓰기 틀린 것도 섞기 ("송금좀", "안되니까", "ㅠㅠ")

**일상 대화 (`benign`) — 헷갈리게 쓰는 게 핵심**
- 위험 단어가 **들어있지만** 사기는 아닌 대화
  - 예: "엄마 폰 고장나서 수리 맡겼어", "회비 3만원 오늘까지 보내줘", "경찰서 가서 분실물 찾았어"
- 위험 단어가 없는 평범한 대화는 테스트 가치가 낮습니다

### JSON 주의사항
- 문장 안에 큰따옴표 `"`를 쓰면 `\"`로 적기
- 항목 사이에 쉼표 `,` 빠뜨리지 않기 (마지막 항목 뒤에는 쉼표 없음)
- 저장 후 3장의 테스트를 돌려서 에러가 안 나면 형식은 맞은 것

## 3. 실기기에서 놓친 대화 기록하기

앱이 **확실한 사기 대화를 못 잡았을 때**, 같은 파일에 이렇게 넣습니다.

```json
{
  "id": "FM-D-선한01",
  "category": "가족사칭",
  "kind": "danger",
  "author": "김선한",
  "source": "real-failure",
  "note": "2026-09-16 갤럭시 카톡, 알림 안 뜸",
  "text": "화면에 보였던 메시지 그대로"
}
```

- `source`를 **`"real-failure"`** 로 쓰면, 이후 규칙 수정에서 **이 대화를 반드시 잡아야 테스트가 통과**합니다.
- `note`에 날짜·기기·앱을 적어주세요.
- 알림이 안 떴더라도 **먼저 앱의 기록 탭을 확인**하세요. 기록이 있으면 탐지는 된 거고 알림 쪽 문제입니다.
- 홈에 노란 **"보호가 멈출 수 있어요"** 줄이 보이면 휴대폰 절전 때문에 앱이 멈춰 있던 겁니다. 눌러서 허용한 뒤 다시 테스트하세요. (삼성은 디바이스 케어 > 백그라운드 사용 한도에서 "딥 절전 앱"에 SafeLink가 없는지도 확인)
- `text`에는 **상대가 보낸 메시지를 화면 순서대로, 말풍선 하나 = 한 줄**로 넣으세요. 한 문장을 말풍선 여러 개로 나눠 보냈으면 나눈 그대로 적는 게 실제 상황과 같습니다.
- 같은 대화방에서 메시지가 이어서 오면 기록은 **하나로 합쳐져** 최신 원문으로 갱신됩니다(10분 안). 기록이 하나뿐이어도 정상이에요.

### 앱 화면 글자(버튼·시각 등)가 기록 원문에 섞여 있으면
탐지 문제가 아니라 화면 요소 거르기 문제입니다. 원문 그대로 재겸에게 보내주세요.
(수정 위치: `android/app/src/main/java/com/safelink/app/data/repository/ScreenTextCleaner.kt` + 같은 폴더 테스트 `ScreenTextCleanerTest`에 실제 줄을 넣어 확인)

### 읽는 법 (숫자는 예시)
```
| 구분 | 개발용 | 확인용(holdout) |
| 위험 대화 탐지율 (경고 이상) | 77% (44/57) | 40% (8/20) |
| 일상 대화 오탐률 (경고 이상) | 0% (0/48)  | 5% (1/20)  |
```
- **탐지율**: 위험 대화 중 **경고(31점) 이상**이 나온 비율. 높을수록 좋음
- **오탐률**: 일상 대화 중 **경고 이상**이 나온 비율. 낮을수록 좋음
- **개발용**: 규칙 수정에 쓰는 문장 / **확인용(holdout)**: 여러분이 쓴 문장 → **발표에 쓰는 숫자는 확인용**
- 아래 "사례별" 표에서 **놓침**(못 잡음) / **오탐**(잘못 잡음) 표시를 볼 수 있어요

## 5. (규칙 수정자용) 패턴 추가하는 법

### 수정할 파일 — **3곳을 똑같이**
```
android/app/src/main/assets/keyword.json      ← 앱이 실제로 쓰는 파일
data/keyword.json                              ← 팀 원본 사본
android/app/src/test/resources/keyword.json    ← 테스트용 사본
```
하나만 고치면 사본끼리 어긋납니다. 새 세부유형을 만들면 `institutions.json`도 3곳 모두 매핑 추가.

### 행동 패턴 항목 형식
```json
{
  "id": "FM-4-1-101",
  "category": "가족사칭",
  "subcategory_id": "4-1",
  "subcategory": "사칭진입",
  "match_type": "regex-simple",
  "pattern": "(휴대\\s*폰|핸드\\s*폰|폰)\\s*(이|을|가)?\\s*(고장|먹통|깨졌|액정|잃어버|분실)",
  "weight": 18,
  "repeat_decay": true,
  "description": "휴대폰 고장·분실을 이유로 한 연락",
  "source": "9주차 행동 패턴 보강(회귀 테스트 기반)",
  "sample": "엄마 휴대폰이 고장나서 그래"
}
```
| 규칙 | 이유 |
|---|---|
| id 일련번호 **1xx** | 행동 패턴으로 추가한 항목 표시 |
| `sample` **필수** | 이 문장이 패턴에 안 걸리면 `DataIntegrityTest`가 실패 |
| 단어 하나가 아니라 **행동+대상**을 묶기 | "안 돼" 단독은 일상어 → "전화/통화 + 안 돼"로 |
| 기존 키워드와 겹치면 **가중치를 기존 이상**으로 | 겹치는 구간은 긴 쪽만 점수에 들어가서, 가중치가 낮으면 오히려 점수가 떨어짐 |
| 같은 세부유형에 여러 패턴 OK | 같은 세부유형 두 번째부터 0.5배라 점수가 폭주하지 않음 |

| 패턴 안의 "아무 글자"는 **`[^\n]{0,15}`** 로 | 한 말풍선 안에서만 찾게 한다. 말풍선을 넘어 이어진 문장은 엔진이 따로 처리한다(아래 5) |

### 점수가 매겨지는 방식 (요약)
1. 키워드·패턴 가중치 합 — 같은 세부유형이 여러 번 나오면 **가장 강한 표현 1개는 온전히, 나머지는 0.5배** (등장 순서 무관)
2. 같은 유형에서 **서로 다른 세부유형** 2개 +10 (둘 중 하나가 돈·인증정보 요구, 링크·앱 설치, 협박 같은 요구·위협일 때만) / 3개 +15 / 4개 +25
3. 전용 조합 규칙·상황 규칙 가산
4. 점수 제한: "사기 조심하래" 같은 **경고 대화**, 요구 없이 **가족사칭 표현만** 있는 대화는 30점(주의)까지
5. 말풍선 경계: 한 문장을 여러 말풍선으로 나눠 보내도("인증번호 오면" / "바로 알려줘") 이어서 찾는다. 단 **앞 말풍선이 문장으로 끝났으면**("~요", "~다", "?") 잇지 않는다
6. 합계로 위험도: 0~15 안전 / 16~30 주의 / **31~65 경고(알림)** / 66~ 긴급
7. (AI 동의 시) 백그라운드에서 10~30점 대화는 AI가 한 번 더 보고, **+16 이상 올려 31점을 넘기면** 알림

### 수정 후 반드시
```bash
./gradlew :app:testDebugUnitTest
```
- `RuleRegressionTest`: 탐지율 **75% 이상**, 오탐률 **5% 이하**, 실제 놓침 **전부 탐지**여야 통과
- `BubbleSplitTest`: 말풍선을 나눠 보내도 95% 이상 유지
- `DataIntegrityTest`: 모든 패턴의 `sample`이 매칭되는지, keyword.json **3곳이 똑같은지**
- `DetectionEngineTest`: 기존 점수 기대값 (바뀌면 이유를 주석으로 남기고 갱신)
- `EvidenceTextTest`: `condition`·`description`에 규칙 id(`VP-1-2-001`)나 영문 식별자(`requires_any`)를 쓰면 실패 — 사용자 화면에 그대로 보이는 문구라서

### 금지
- **확인용(holdout) 문장을 보고 규칙을 고치지 않기.** 고쳤다면 그 문장들은 `source`를 `"draft-2"` 등 개발용으로 바꾸고, 새 확인용 문장을 다시 받는다.
- 기준값(75%·5%)을 **내리지 않기.** 좋아지면 올린다.
