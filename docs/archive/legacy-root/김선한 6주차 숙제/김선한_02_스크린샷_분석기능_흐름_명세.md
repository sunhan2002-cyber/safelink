# 김선한 6주차 숙제 02 - 스크린샷 분석 기능 흐름 명세

## 1. 기능 목적

스크린샷 분석 기능은 사용자가 대화 내용을 직접 입력하지 않아도, 채팅 스크린샷을 선택해 OCR로 텍스트를 추출하고 기존 SafeLink 분석 엔진으로 넘길 수 있게 만드는 기능이다.

이 기능의 목적은 `입력 방식 확장`이다. 즉, 분석 엔진 자체를 새로 만드는 것이 아니라 `스크린샷 -> 텍스트 -> 기존 분석 흐름`으로 자연스럽게 연결하는 데 초점을 둔다.

## 2. 시작 위치

- `HomeScreen`에서 대화 분석 진입
- `DetectionInputScreen`에서 입력 방식 선택
- 입력 방식 중 `스크린샷 업로드` 선택

## 3. 기본 흐름

```text
HomeScreen
-> DetectionInputScreen
-> 스크린샷 업로드 선택
-> PhotoPicker에서 이미지 선택
-> 선택 이미지 썸네일 표시
-> 분석 시작
-> OCR 수행
-> originalText 또는 분석용 텍스트 구조 생성
-> 1차 규칙 기반 분석
-> 필요 시 2차 AI API 보조 분석
-> DetectionResultScreen
-> ResponseGuideScreen
```

## 4. 김재겸 6week 기준 현재 반영 방향

노션 기준으로 현재 반영해야 할 구현 내용은 아래와 같다.

- `data/ocr/OcrService.kt`
  - OCR 추상화 인터페이스
- `data/ocr/StubOcrService.kt`
  - 시연용 임시 OCR 구현
- `DetectionInputScreen.kt`
  - PhotoPicker로 갤러리 열기
  - 썸네일 표시
  - 이미지 삭제
  - 분석 시작 버튼 연결
- `DetectionViewModel.kt`
  - `selectedImages` 관리
  - `runOcrOnSelectedImages()` 수행
  - OCR 결과를 `originalText`에 채우는 구조

## 5. 입력 방식 기준

### 이번 주 기준 확정

- 사용자는 갤러리에서 스크린샷을 직접 선택한다.
- 다중 이미지 선택은 허용하되, 실제 적용 범위는 팀이 다시 확인한다.
- 사용자가 선택한 이미지는 앱 안에서 썸네일로 확인 가능해야 한다.
- 사용자는 분석 시작 전에 선택 이미지를 삭제할 수 있어야 한다.

### 입력 이후 처리 기준

- OCR 결과는 기존 분석 엔진이 읽을 수 있는 형태로 합쳐야 한다.
- 우선순위는 `originalText` 하나로 합치는 방식이 가장 높다.
- 이후 필요하면 turn list 형태로 확장할 수 있다.

## 6. OCR 처리 기준

### 현재 기준

- 이번 단계에서는 실제 OCR 완성보다 `OCR이 어디서 수행되고 어디로 넘어가는지`가 중요하다.
- 시연 단계에서는 `StubOcrService`로 흐름을 먼저 보여줄 수 있다.
- 실제 OCR 연결은 `OcrService` 구현체 교체 방식으로 붙인다.

### 월요일 전 팀이 다시 확인할 것

- 실제 OCR 구현체를 기기 내에서 처리할지 서버로 보낼지
- OCR 결과를 한 문단으로 합칠지, 문장 단위로 나눌지
- 다중 이미지 입력 시 순서를 어떻게 보장할지

## 7. 예외 처리 항목

- 이미지를 선택하지 않고 분석 시작을 누른 경우
- OCR 결과가 비어 있는 경우
- OCR 결과가 너무 짧아서 분석이 어려운 경우
- 지원하지 않는 이미지 형식이 들어온 경우
- 여러 장 업로드 시 순서가 꼬인 경우

## 8. 예외 처리 문구 기준

- 이미지가 없으면 분석 시작 불가
- 텍스트 추출 실패 시 재선택 안내
- 텍스트가 너무 적으면 직접 입력 유도
- 이미지가 너무 흐리거나 잘린 경우 재선택 유도

문구 자체는 김우영 최종 문구 가이드 기준에 맞춰 적용한다.

## 9. 분석확장과의 연결 기준

- 스크린샷 분석은 입력 방식만 다를 뿐, 분석 기준은 텍스트 입력과 동일해야 한다.
- OCR로 나온 텍스트도 먼저 `1차 규칙 기반 분석`을 수행한다.
- 규칙 기반만으로 판단이 약한 경우에만 `2차 AI API 보조 분석`으로 넘긴다.
- 결과 화면과 대응 가이드 화면은 기존 텍스트 입력 결과와 동일한 구조를 사용한다.

## 10. 구현 완료 판단 기준

- 사용자가 앱 안에서 스크린샷 분석 진입 흐름을 이해할 수 있어야 한다.
- 스크린샷 선택 -> 썸네일 확인 -> 분석 시작 흐름이 끊기지 않아야 한다.
- OCR 결과가 기존 분석 흐름으로 넘어가는 구조가 문서상 명확해야 한다.
- 김재겸이 구현한 구조를 김선한 문서 기준으로 설명할 수 있어야 한다.

## 11. 한 줄 결론

스크린샷 분석 기능의 핵심은 `새 분석 엔진 개발`이 아니라, `새 입력 방식이 기존 분석 엔진으로 안정적으로 합류하도록 만드는 것`이다.
 
## 12. 현재 구현 상태 보충

- 현재 분석 엔진 자체는 실제로 동작한다.
- 사용자가 넣은 텍스트는 `keyword.json` 기준으로 실제 점수 계산을 수행한다.
- 현재 임시인 부분은 `스크린샷 -> 텍스트 추출` 단계뿐이다.
- 지금 `StubOcrService`는 사용자가 고른 실제 이미지를 읽지 않고, 미리 정해둔 예시 문장을 반환한다.
- 그래서 어떤 이미지를 넣어도 OCR 결과는 같고, 분석 결과도 같은 예시 흐름으로 이어질 수 있다.
- 즉 현재 스크린샷 분석은 `선택 -> 추출 -> 분석 -> 결과` 흐름을 시연하는 단계이지, 사진 속 실제 텍스트를 읽는 완성형 OCR 단계는 아니다.

## 13. 실제 OCR 전환 시 교체 지점

- `build.gradle`에 `com.google.mlkit:text-recognition-korean` 추가
- `MlKitOcrService` 구현
  - 이미지 URI를 받아 ML Kit로 실제 텍스트 추출
- `DetectionViewModel`에서 `StubOcrService()`를 `MlKitOcrService()`로 교체

## 14. 구현 시 추가 고려사항

- ML Kit OCR은 비동기 처리이므로 현재 동기식 `extractText()` 구조를 `suspend` 기반으로 바꾸는 것이 자연스럽다.
- OCR 수행 중에는 로딩 상태를 보여줘야 한다.
- 이 방식은 온디바이스 처리라서 개인정보 원칙과도 맞는다.
