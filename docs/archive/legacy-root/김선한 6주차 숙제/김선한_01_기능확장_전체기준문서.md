# 김선한 6주차 숙제 01 - 기능확장 전체 기준 문서

## 1. 문서 목적

이 문서는 SafeLink의 기능확장 파트를 `김선한`과 `김재겸` 기준으로 정리한 공통 기준 문서다.

이번 숙제의 핵심은 실제 기능을 새로 구현한 결과물을 제출하는 것이 아니라, `월요일인 2026년 8월 3일 대면 회의에서 바로 구현에 들어갈 수 있도록 기능확장 기준을 정리하는 것`이다.

즉 이번 문서는 `구현 결과물 문서`가 아니라 `구현 준비 문서`다.

## 2. 담당 범위

### 기능확장 담당

- 김선한
- 김재겸

### 이번 문서에서 다루는 범위

- 스크린샷 분석 기능이 어디서 시작되고 어디로 이어지는지
- 백그라운드 감지 기능이 어떤 구조로 붙는지
- 기능확장 파트가 기존 앱 흐름과 어떻게 연결되는지
- 월요일 회의에서 어떤 기준으로 바로 구현을 시작할지

### 이번 문서에서 직접 다루지 않는 범위

- 신기훈의 분석확장 세부 구현
- 김우영의 문구 세부 설계
- 전체 팀원의 역할 정리 문서

위 내용은 필요할 때 `연동 기준`으로만 참고한다.

## 3. 이번 숙제의 성격

이번 숙제에서 김선한이 한 것은 아래와 같다.

- 기능확장 전체 기준 정리
- 스크린샷 분석 흐름 정리
- 백그라운드 감지 요구사항 정리
- 월요일 회의용 체크리스트 정리
- 기능확장 파트에서 바로 구현할 수 있도록 기준 확정
- 설정 화면에 기능확장 관련 항목을 실제 화면 코드로 반영

이번 숙제에서 김선한이 하지 않은 것은 아래와 같다.

- 실제 OCR 기능 구현
- 실제 백그라운드 감지 서비스 구현
- 실제 화면 동작 반영

즉, 이번 숙제는 대부분 `구현 기준 정리`이지만, 설정 화면 기준으로는 `기능확장 관련 UI 반영 1건`이 포함되어 있다.

## 4. 기능확장 기본 방향

- 기존 텍스트 분석 흐름은 유지한다.
- 기능확장은 기존 앱 흐름을 깨지 않고 옆에 붙는 방식으로 확장한다.
- 이번 주 기준에서는 `완성도`보다 `구현 가능한 구조 확정`을 우선한다.
- 스크린샷 분석과 백그라운드 감지는 모두 기존 결과 화면과 대응 가이드 화면으로 연결되어야 한다.

## 5. 현재 확정된 기능확장 구조

### 5-1. 스크린샷 분석 흐름

```text
HomeScreen
-> DetectionInputScreen
-> 스크린샷 업로드 선택
-> 이미지 선택
-> OCR 수행 준비
-> 기존 분석 흐름으로 연결
-> DetectionResultScreen
-> ResponseGuideScreen
```

### 5-2. 백그라운드 감지 흐름

```text
설정에서 기능 ON
-> 감지 서비스 구조 동작
-> 위험 신호 감지 시도
-> 알림 표시
-> 알림 클릭
-> 결과 화면 또는 대응 가이드 화면 이동
```

## 6. 김재겸 6week 기준 반영 내용

김재겸 노션 `6week` 기준으로 현재 기능확장 파트는 아래 방향으로 반영된다.

### 스크린샷 분석 쪽

- `OcrService.kt`
- `StubOcrService.kt`
- `DetectionInputScreen.kt`
- `DetectionViewModel.kt`

핵심은 `스크린샷 -> OCR -> 기존 분석 흐름 연결`이다.

### 백그라운드 감지 쪽

- `MessageDetectionService.kt`
- `RiskNotifier.kt`
- `Manifest`
- `accessibility_service_config.xml`

핵심은 `감지 -> 알림 -> 화면 이동 구조 자리 확보`다.

## 7. 김선한 역할의 개발 관점 의미

김선한 역할은 단순 문서 작성이 아니다.

이번 주 기준에서 김선한 역할은 아래와 같다.

- 어떤 기능부터 구현할지 기준을 잡는다.
- 스크린샷 분석 기능의 시작점과 연결점을 확정한다.
- 백그라운드 감지 기능이 어디에 붙는지 확정한다.
- 김재겸이 구현할 수 있도록 기능 명세를 개발 기준으로 정리한다.

즉, 이번 숙제는 `직접 코딩한 개발 숙제`는 아니지만 `기능확장 개발 기준을 정하는 숙제`라고 보는 게 맞다.

## 8. 월요일 회의 전 완료되어야 하는 것

- 스크린샷 분석 기능 시작 위치 확정
- OCR 결과가 기존 흐름으로 들어가는 방식 확정
- 백그라운드 감지 구조 확정
- 알림 이후 어느 화면으로 이동할지 확정
- 김재겸이 바로 구현 시작 가능한 수준까지 기능 범위 확정

## 9. 한 줄 결론

이번 김선한 6주차 숙제는 `기능확장 실제 구현`이 아니라 `기능확장 구현 기준 확정`이 핵심이다.

## 10. 현재 상태 보충

### 스크린샷 분석

- 현재 상태는 `분석 엔진은 실제`, `OCR만 시연용 Stub`이다.
- 즉 스크린샷 분석 화면 흐름은 실제로 연결돼 있지만, 사진 속 실제 텍스트를 읽는 단계는 아직 아니다.
- 현재 `StubOcrService`가 고정 예시 문장을 반환하므로 어떤 이미지를 넣어도 같은 예시 분석 결과로 이어질 수 있다.
- 실제 OCR 전환은 `OcrService` 구현체 교체 방식으로 준비돼 있다.
- 추후 ML Kit OCR을 붙일 때는 라이브러리 추가, 구현체 추가, ViewModel 교체가 필요하다.
- ML Kit는 비동기 처리라서 추후 `suspend` 구조와 로딩 UI도 같이 필요하다.

### 최신 반영사항

- 2026-08-05 기준 최신 GitHub 반영으로 대화 분석 세션 상태 초기화 문제가 수정되었다.
- `DetectionViewModel.reset()`과 `switchMode()`가 추가되어 홈에서 다시 진입하거나 입력 방식을 바꿀 때 이전 입력값, 이미지, 결과값이 남지 않도록 정리됐다.
- 즉 스크린샷 분석/텍스트 분석 흐름 자체는 이전보다 안정적으로 다시 시작할 수 있는 상태가 되었다.

## 11. 현재 분석 구조 문제상황

- 현재 앱의 1차 위험도 분석 로직은 키워드 / regex / combo 중심으로 동작하고 있다.
- 팀이 정리한 문장 기반 / 상황 기반 분석 기준은 위험도 계산 본체에 직접 반영되지 않았다.
- 대신 `shouldEscalateToAI()`에 들어가 있어서, `AI 보조분석으로 넘길지 판단하는 조건`으로만 쓰이고 있다.
- 그래서 현재 구현은 문장 의미나 상황 맥락을 1차 분석에서 직접 반영하지 못하고 있다.
- 결과적으로 기획했던 하이브리드 1차 분석 구조와 실제 코드 구조가 어긋나 있다.

## 12. 원래 기획 의도

- 1차 분석에서
  - 키워드 기반 분석
  - 문장 기반 규칙 분석
  - 상황 기반 규칙 분석
  을 함께 반영해서 온디바이스 위험도를 산출하는 것이 원래 의도였다.
- 2차 분석은
  - 1차 분석 결과가 애매한 경우
  - 1차 규칙 기반 분석으로 놓칠 가능성이 있는 경우
  에만 AI API가 보조 판단을 해주는 구조여야 했다.
- 즉 AI는 메인 분석기가 아니라, 1차 분석을 보완하는 2차 보조 분석 역할이 의도였다.

## 13. 해결 방향

- 문장 기반 / 상황 기반 규칙을 `shouldEscalateToAI()`가 아니라 `DetectionEngine.analyze()` 내부 점수 계산 로직에도 반영해야 한다.
- 예를 들어
  - 반복 압박 문장 패턴
  - 장기 유도 / 미래 약속 / 관계 고립
  - 책임 전가 / 기억 부정 / 죄책감 유도
  같은 규칙에 별도 점수나 보정치를 부여하는 방식으로 1차 분석에 포함해야 한다.
- 그 다음 `shouldEscalateToAI()`는
  - 회색지대 점수
  - 규칙 충돌
  - 장기 대화 맥락 필요
  - 사람이 직접 위험 신고
  같은 `애매한 경우 AI로 넘기는 조건`만 담당하도록 역할을 분리해야 한다.
- 마지막으로 결과 화면에서도
  - 어떤 키워드가 잡혔는지
  - 어떤 문장/상황 규칙이 적용됐는지
  를 함께 보여줘야 팀이 의도한 분석 흐름이 사용자에게도 보이게 된다.
