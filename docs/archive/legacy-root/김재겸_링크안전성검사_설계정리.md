- 작성: 김재겸 (기능확장)
- 일자: 2026-09-09
- 관련 문서: `김재겸_본선준비_기능보완_정리.md`, `docs/인스타DM_감지_실기기검증.md`

## 1. 무엇을 만들었나

대화·문자에 섞여 온 **링크가 실제로 위험한 주소인지** 확인하는 기능입니다.

기존 온디바이스 엔진은 "지금 당장", "명의 도용" 같은 **문구**로 위험을 판단합니다.
그런데 실제 스미싱에는 문구를 거의 넣지 않고 **링크만 툭 던지는 형태**가 많습니다.

```
[Web발신] 주소불일치로 택배가 반송되었습니다 hxxp://kr-post[.]top/chk
```

이런 건은 키워드 점수가 낮게 나와 기존 경로로는 그냥 지나갑니다.
링크 자체를 검사해야 잡을 수 있습니다.

---

## 2. **왜 이 방식을 골랐는가 — 보안이 이유입니다** ⭐

이 기능은 구현 방법이 두 가지이고, **어느 쪽을 고르느냐가 곧 개인정보 설계**입니다.
SafeLink는 성능이 아니라 **보안 문제 때문에** 두 번째 방식을 선택했습니다.

| | ① 실시간 조회 방식 | ② **온디바이스 차단 목록 방식 (채택)** |
|---|---|---|
| 동작 | 검사할 URL을 **서버로 보내서** 물어봄 | 위험 URL 해시 목록을 **기기에 내려받아 두고**, 기기 안에서 대조 |
| 서버가 알게 되는 것 | **사용자가 언제 어떤 링크를 받았는지 전부** | **아무것도 없음** — 목록을 내려받을 뿐 |
| 오프라인 | 불가 | **가능** |
| 속도 | 네트워크 왕복 필요 | 로컬 조회 (수 ms) |

### 왜 ①을 쓰면 안 되는가

SafeLink는 **피해자의 대화**를 다루는 앱입니다.
①을 쓰면 링크 하나하나가 외부로 나가고, 그 순간

> "누가 · 언제 · 어떤 사기 링크를 받았는지"

가 그대로 외부 기록으로 남습니다. 이는 앱 전체를 관통하는 원칙인
**"원문은 서버로 전송하지 않는다"** 와 정면으로 어긋납니다.

특히 이 기능은 **백그라운드에서도 돌아갑니다.** 사용자가 인지하지 못한 채
화면에 뜬 링크가 계속 외부로 나가는 구조는 받아들일 수 없습니다.

### ②가 성립하는 이유

기기에 내려받는 것은 URL 원문이 아니라 **위험 URL의 SHA-256 해시 앞부분(약 4바이트)** 입니다.
검사는 "내가 가진 링크의 해시가 이 목록에 있나"를 **기기 안에서** 대조하는 방식이라,
바깥으로 나가는 정보가 없습니다.

Google 문서도 이 방식에 대해 명시합니다.

> 검사 중인 URL을 Google이 알게 되는 시점은 없습니다.
> — Google Web Risk / Safe Browsing Update API 문서

### 자주 나오는 반문 두 가지

**Q. 목록을 기기에 내려받으면, 악성앱이 그 목록을 훔쳐볼 수 있지 않나?**
목록에 들어 있는 건 **이미 공개된 "위험한 사이트 명단"의 해시**입니다.
사용자 개인정보가 아니므로 유출돼도 잃을 것이 없습니다.
반대로 ①은 **사용자가 받은 링크**라는 개인정보가 흐르므로 성격이 완전히 다릅니다.

**Q. 백그라운드로 계속 돌면 느리지 않나?**
로컬 대조라 네트워크 왕복이 없어 오히려 ①보다 빠릅니다.
그래도 상한(2초)을 둬서, 목록 준비 중 등으로 지연되면 기다리지 않고 넘어갑니다.

## 3. 구현 방식

직접 프로토콜을 구현하지 않고 **Google Play 서비스가 제공하는 클라이언트**를 씁니다
(`com.google.android.gms:play-services-safebrowsing:16.0.0`).

목록 다운로드·주기적 갱신·해시 대조를 Play 서비스가 관리하므로

- 앱이 목록 DB를 직접 들고 있을 필요가 없고
- **기기 전체가 목록 하나를 공유**하므로 앱 용량·트래픽이 늘지 않습니다

프로토콜은 `Protocol.LOCAL_BLOCK_LIST` 로 **고정**합니다.
같은 API에 `REAL_TIME`(위 표의 ①)도 있지만, 위에 적은 이유로 쓰지 않습니다.

### 파일 구성

| 파일 | 역할 |
|---|---|
| `data/link/LinkExtractor.kt` | 원문에서 링크를 찾아냄 (Android 의존 없음 → 유닛 테스트 대상) |
| `data/link/LinkRiskResult.kt` | 판정 결과 모델 (위험/미등재/검사불가, 위협 4분류) |
| `data/link/LinkRiskChecker.kt` | Play 서비스 클라이언트 호출, 상태코드 → 앱 문구 변환 |
| `ui/screens/detection/DetectionViewModel.kt` | 분석 시 링크 검사 비동기 실행 |
| `ui/screens/detection/DetectionResultScreen.kt` | 결과 화면 "링크 검사" 섹션 |
| `background/MessageDetectionService.kt` | 백그라운드에서 악성 링크 단독 감지 |

### 링크 추출에서 신경 쓴 것

스미싱 링크는 필터를 피하려고 **일부러 망가뜨려** 옵니다. 아래를 모두 같은 링크로 봅니다.

```
https://evil.com/x        그대로
hxxps://evil.com/x        scheme 훼손
evil[.]com/x              점 훼손
evil(dot)com/x            점을 글자로
bit.ly/abcd               scheme 생략
여기클릭bit.ly/abcd하세요     한글에 딱 붙은 링크
```

훼손해서 보냈다는 **사실 자체가 위험 신호**이므로 화면에 따로 알려줍니다.

> "주소를 일부러 변형해 보낸 링크입니다. 차단을 피하려는 수법입니다."

반대로 오탐은 사용자를 지치게 하므로 보수적으로 잡습니다.
scheme이 없는 후보는 **알려진 TLD로 끝날 때만** 링크로 인정합니다.
그래서 `버전 1.0`, `설명.txt`, `오전 9.30`, `help@example.com` 은 걸리지 않습니다.

### 백그라운드 동작

키워드로 **위험이 안 잡힌 화면**에서만 링크를 검사합니다
(키워드로 이미 알림이 나갔으면 중복 알림을 만들지 않습니다).

악성 링크가 확인되면 위험도 **긴급(CRITICAL)** 으로 알립니다.
키워드 점수는 정황 추정값이지만, 차단 목록 등재는 **"악성으로 확인된 주소"라는 사실 판정**이기 때문입니다.

같은 주소는 30분간 다시 알리지 않습니다(스크롤·재진입 모두 같은 사건).

## 4. 화면 문구에서 지킨 원칙

**"안전합니다"라고 절대 쓰지 않습니다.**

차단 목록에 없다는 건 "안전하다"가 아니라 **"아직 신고되지 않았다"** 는 뜻이고,
새로 만든 스미싱 도메인은 대개 등재 전입니다.
여기서 "안전합니다"라고 써 버리면 **앱이 오히려 사용자를 안심시켜 링크를 누르게 만듭니다.**

| 판정 | 화면 문구 |
|---|---|
| 위험 | "피싱·사칭 사이트" + 위협 설명 |
| 미등재 | "알려진 위험 목록에는 없습니다" + "아직 신고되지 않은 새 주소일 수 있으니, 모르는 사람이 보낸 링크는 열지 마세요." |
| 검사 불가 | 사유 표시 + "직접 확인이 필요합니다" |

섹션 마지막에는 검사 방식을 밝힙니다.

> "링크 주소는 외부로 전송되지 않으며, 기기에 저장된 위험 주소 목록과 대조했습니다."

### 출처 표기는 선택이 아니라 의무

구글 데이터로 경고를 띄우는 앱은 **"Advisory provided by Google" 표기와 안내 페이지 링크를 반드시 넣어야** 합니다.

> 위험 페이지 경고를 표시할 때는 "Advisory provided by Google"을 Safe Browsing 안내
> 페이지 링크와 함께 포함해야 합니다.
> — Safe Browsing 이용 조건

그래서 링크 검사 섹션 맨 아래에 이 표기를 넣고 안내 페이지로 연결했습니다.
구글 데이터를 실제로 쓴 경우에만 표기하고, 검사 자체가 실패했을 때는 표기하지 않습니다.
문구는 규정된 영문 그대로 두고 임의로 번역하지 않았습니다.

## 5. 검증

### 유닛 테스트

`LinkExtractorTest` 18건 신규. 전체 **132건 통과**.
정상 링크 / 훼손 링크(`hxxp`, `[.]`, `(dot)`) / 한글 밀착 / 문장부호 / 중복·대소문자 /
오탐 방지(버전번호·파일명·이메일) / 실제 택배 스미싱 문구.

### 에뮬레이터 실기 검증 — 악성 URL 판정

구글이 제공하는 테스트용 악성 주소로 확인했습니다.

```
입력: link: http://testsafebrowsing.appspot.com/s/phishing.html

링크 검사
  피싱·사칭 사이트
  http://testsafebrowsing.appspot.com/s/phishing.html
  기관이나 지인을 사칭해 계정·금융정보를 가로채는 것으로 신고된 주소입니다.
  링크 주소는 외부로 전송되지 않으며, 기기에 저장된 위험 주소 목록과 대조했습니다.
  Advisory provided by Google
```

### **오프라인 검증 — 이 기능의 핵심 근거** ⭐

같은 주소를 **기기를 완전히 오프라인으로 만든 뒤** 다시 검사했습니다.

```
비행기 모드 ON + Wi-Fi/데이터 OFF
→ dumpsys connectivity: "Active default network: none"   (네트워크 전무)

같은 링크 재검사 → 여전히 "피싱·사칭 사이트" 로 정확히 판정
```

네트워크가 아예 없는 상태에서 악성 판정이 나왔다는 것은,
**그 판정이 기기 안의 목록만으로 이뤄졌다는 뜻**입니다.
URL을 어딘가로 보내서 물어본 게 아니라는 것을 실제로 보여주는 결과입니다.

2장의 설명이 말로만이 아니라 실제로 그렇게 동작한다는 근거이므로,
심사에서 "정말 안 보내는 게 맞느냐"는 질문이 나오면 이 검증을 제시하면 됩니다.

> **주의 — 발표 때 헷갈리지 말 것**: 에뮬레이터는 평소에도 `ping` 이 실패합니다(ICMP 차단).
> ping 실패는 오프라인의 증거가 아닙니다. 위 검증은 비행기 모드로 실제 네트워크를 끊고
> `Active default network: none` 을 확인한 뒤 진행한 것입니다.

### 아직 확인하지 못한 것 — 백그라운드 링크 감지

**수동 분석 경로는 위와 같이 완전히 검증됐습니다.**
백그라운드 경로는 코드가 연결돼 있으나 **실제로 알림이 뜨는 것까지는 확인하지 못했습니다.**
검사기(`LinkRiskChecker`)는 수동 경로와 완전히 같은 것을 쓰므로 판정 자체는 동일하게 동작합니다.

확인이 막힌 이유는 링크 기능과 무관한 **텍스트 수집 단계의 문제**였습니다.

| 화면 | 관찰된 동작 |
|---|---|
| 문자 목록 화면 | 미리보기 텍스트가 수집됨 → 정상 동작. 다만 기존 한글 스미싱 문자가 남아 있어 **키워드 경로가 먼저 잡고 링크 검사까지 가지 않음**(설계대로) |
| 대화방 화면 | `rootInActiveWindow` 가 대화 말풍선이 아니라 **입력창 영역만** 돌려줌 (85자: "Text message / 이모티콘 / 음성메시지"). 대화방에 새 문자가 도착해도 이벤트가 오지 않음 |

즉 대화방 안에서는 **링크뿐 아니라 키워드 감지도 화면 내용을 못 읽고 있습니다.**
링크 기능 이전부터 있던 문제이며, 이번 작업으로 생긴 것이 아닙니다.

**확인 필요**: 이 현상이 에뮬레이터/구글 메시지 특정 버전 문제인지, 실기기에서도 같은지.
실기기 카카오톡·문자로 재현해 봐야 판단할 수 있습니다. 별도 작업으로 다루는 것이 맞습니다.

## 6. API 키

키는 발급받아 `android/local.properties` 에 넣어 두었습니다(이 파일은 `.gitignore` 대상이라
저장소에 올라가지 않습니다). 위 검증은 모두 이 키로 진행한 것입니다.

```
SAFE_BROWSING_API_KEY=발급받은_키
```

팀원이 각자 빌드하려면 같은 줄을 자기 `local.properties` 에 넣어야 합니다.
키가 없으면 **링크 검사만 조용히 비활성**되고 분석·알림·기록은 그대로 동작합니다.

### 키 관리에서 챙길 것

- Google Cloud Console 에서 이 키를 **Android 앱(패키지명 + SHA-1)으로 제한**해 두는 것이 좋습니다.
  제한이 없으면 키가 유출됐을 때 남이 우리 할당량을 쓸 수 있습니다.
- 키를 소스코드에 직접 적지 않았습니다. 커밋 대상이 아닙니다.

### 라이선스 — 팀이 알고 있어야 할 부분

Safe Browsing API 는 **비상업적 용도에 한해 무료**입니다.

> Safe Browsing API 는 비상업적 용도 전용입니다("판매 또는 수익 창출 목적이 아닌"이라는 의미).
> 악성 URL 탐지를 상업적 목적으로 사용해야 한다면 Web Risk API 를 참고하십시오.
> — Safe Browsing 이용 조건

대회 출품·연구 목적은 여기에 해당합니다.
다만 **실제 상용 출시를 검토하는 시점에는 Web Risk API 로 전환해야 합니다.**
Web Risk 도 같은 온디바이스 대조 방식(Update API)을 지원하므로,
**이 문서에서 설명한 개인정보 보호 구조는 그대로 유지됩니다.** 바뀌는 것은 요금 체계뿐입니다.

## 7. 보고서·발표에 쓸 문장

> SafeLink 는 대화에 포함된 링크가 실제 악성 주소인지 함께 확인합니다.
> 이때 **검사할 링크를 외부로 전송하지 않습니다.**
> 위험 주소 목록을 기기에 미리 내려받아 두고 기기 안에서 대조하는 방식이라,
> 사용자가 어떤 링크를 받았는지는 외부에 남지 않습니다.
>
> 링크를 서버로 보내 물어보는 실시간 조회 방식이 구현은 더 쉽습니다.
> 그러나 피해자의 대화를 다루는 앱에서, 그것도 백그라운드로 동작하는 경로에서
> "누가 언제 어떤 사기 링크를 받았는지"가 외부 기록으로 남는 것은 허용할 수 없다고 판단해
