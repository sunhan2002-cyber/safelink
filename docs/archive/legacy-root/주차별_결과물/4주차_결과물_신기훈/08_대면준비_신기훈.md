## 1. `shouldEscalateToAI` — 실제 어떤 경우에 동작하는가

`DetectionEngine.shouldEscalateToAI(result, sessionTurnCount, manualReportFlag, newSubcategoryRolloutActive)`.
5개 조건 중 하나라도 맞으면 true (OR 조건):

| # | 조건 | 예시 입력 | 결과 |
|---|---|---|---|
| 1 | 점수 20~40 또는 55~70 (회색지대) | "택배기사인데요, 배송 중 확인 차 연락드렸습니다. 그럼 명의 도용 우려가 있어서 확인이 필요합니다." | score=37 → **호출됨** |
| 2 | 가스라이팅 어조의존 중분류(3-1·3-2·3-7·3-8·3-9) 2회 이상 감지 | "내가 언제 그렇게 말했어?"(3-2) + "걔가 이간질하는 거야"(3-8) | 점수가 낮아도(예: 27점) **호출됨** |
| 3 | 로맨스스캠 FUTURE_FAKE(2-8)·SUNK_COST(2-10) 감지 + 세션 15턴 이상 | "여기까지 왔는데 지금 포기하면 원금까지 묶여요" (긴 대화 뒤에 등장) | 15턴 미만이면 **호출 안 됨**, 15턴 이상이면 **호출됨** |
| 4 | 사용자가 수동으로 "위험한 것 같다" 표시 | (문구/버튼은 아직 미구현 — 함수 파라미터만 준비됨) | 점수·매칭 무관 **항상 호출** |
| 5 | *(한시적)* 4주차 신설 중분류(2-6~2-10, 3-7~3-9) 매칭 시 | "텔레그램으로 옮기실 수 있을까요?"(2-6, MIGRATE) | 점수가 낮아도 **호출됨** (실사용 검증 끝나면 스위치로 끌 수 있음) |

**호출 안 되는 경우 예시**: score=77(명백히 CRITICAL, "이미 확실하니 서버 확인 불필요"),
score=10이면서 위 조건 어디에도 안 걸리는 경우("확실히 안전"). → **20점 미만/70점 이상은
원칙적으로 서버 안 부름**(기존 API 문서 원칙 그대로).

**검증 상태**: 11개 케이스 단위 테스트(`ShouldEscalateToAITest`) 전부 통과, 프로덕션
코드를 실제 목서버에 연결해서 마스킹→호출→병합→네트워크실패폴백까지 실행 확인함 (07번 문서).

## 2. 규칙 기반 분석 결과 ↔ AI 보조 분석 조건 연결 확인

실제 앱 흐름에서 어디에 붙어있는지:

```
DetectionInputScreen (텍스트 입력 또는 스크린샷 업로드)
  -> [스크린샷이면] viewModel.runOcrOnSelectedImages() 로 originalText 채움
  -> AnalyzingScreen 진입 시 viewModel.analyze() 호출
       1. repository.analyze(originalText)         # 온디바이스, 즉시 완료
       2. repository.shouldEscalateToAI(result,..) # 위 5개 조건 판단
       3. true면 viewModelScope에서 escalateToAI() 비동기 호출
  -> DetectionResultScreen: viewModel.result를 그대로 구독
```

**확인된 것**: `DetectionResultScreen`은 `viewModel.result`(Compose state)를 직접 읽기
때문에, AI 보조 분석 응답이 화면 진입 *이후에* 도착해도 **자동으로 재구성돼서 점수가
갱신됨** (별도 로딩 콜백 연결 안 해도 됨 — Compose가 알아서 함). 다만 "AI 분석 중"이라는
시각적 표시는 아직 없음(`viewModel.isEscalatingToAI` 상태값은 만들어놨지만 화면에서 아직
안 씀 — 3장 결과 화면 데이터 참고).

**스크린샷 입력 경로도 동일하게 연결됨**: OCR 결과든 텍스트 직접입력이든 결국
`originalText` 하나로 합쳐져서 이후 흐름은 완전히 같음.

**백그라운드 감지(`MessageDetectionService`)는 아직 AI 연동 전**: `DetectionRepository.analyze()`까지만
연결돼 있고 `shouldEscalateToAI`/`escalateToAI`는 안 붙어있음 (화면 텍스트 추출 자체도
아직 TODO라 지금은 실질적으로 동작 안 함 — 이 부분은 김재겸 확인 필요).

## 3. 결과 화면에 들어가야 하는 데이터 (재확인)

`DetectionResultScreen.kt`가 실제로 쓰는 `DetectionResult` 필드 전부 확인:

| 필드 | 화면에서 쓰는 곳 |
|---|---|
| `riskLevel` | 상태 헤더 색상/아이콘, 대응 가이드 이동 시 라우트 파라미터 |
| `score` | 위험 점수 숫자 표시 |
| `category` | "OO 위험이 감지되었습니다" 문구 |
| `matchedKeywords` | 감지된 위험 요소 태그(subcategoryName), 대화 하이라이트 카드 |
| `recommendedInstitutions` | 추천 기관 카드 목록(rank순) |
| `isSafeAndEmpty` (계산 프로퍼티) | 안전 상태 카드 분기 |

구조 변경 없음 — 01번 문서 이후 한 번도 안 바뀜. AI 보조 분석이 반영해도 `score`/`riskLevel`만
바뀌고 나머지 필드 구조는 그대로라 화면 쪽 추가 대응 불필요.

**작은 정리**: `DetectionResultScreen.kt` 상단 KDoc에 "TODO: 아직 더미데이터 고정 사용 중"이라고
적혀 있던 게 실제로는 이미 다 연결된 뒤에도 안 지워져 있던 걸 발견해서 이번에 고침(오해 방지).

## 5. 규칙 기반으로 잡히는 경우 / 안 잡히는 경우 예시

`신규_기법_문장_수집_v1.json` 기준 38문장 중 **30건(79%) 잡힘, 8건(21%) 안 잡힘**.
대면에서 바로 보여줄 대표 예시:

### 잡히는 예시

| 카테고리 | 입력 | 매칭 |
|---|---|---|
| 보이스피싱 | "제 신분 의심되시면 대검찰청 대표번호 1301로 확인해 보셔도 됩니다." | `VP-1-3-004`(가짜 검증 유도) |
| 로맨스스캠 | "카톡이 여기선 자꾸 끊겨서요. 텔레그램으로 옮기실 수 있을까요?" | `RS-2-6-001`(외부 메신저 유도) |
| 가스라이팅 | "걔가 우리 사이 이간질하는 거 너만 몰라." | `GL-3-8-001`(주변인 신뢰 훼손) |

### 안 잡히는 예시 (원인별 1개씩)

| 원인 | 입력 | 왜 안 잡히나 |
|---|---|---|
| 패러프레이즈(표현 차이) | "무슨 말? 나 그런 말 한 적 없는데." | 기존 "그런 적 없어"와 뜻은 같은데 표현이 달라서 부분일치 안 됨 |
| 숫자 관계 추론 | "3주만에 100이 137 됐죠?" | 100→137이 수익률 37%라는 걸 이해해야 하는데, 키워드 매칭은 산수를 못 함 |
| 어조·함의 의존 | "봐, 지금도 확신 못 하잖아. 나는 너 걱정돼서 하는 말이야." | 문자 그대로는 "걱정"이라는 긍정적 단어라 위험 신호로 안 보임 — 맥락상 몰아붙이는 함의는 키워드로 못 잡음 |

뒤 2개(숫자 추론, 어조 함의)가 **AI 보조 분석이 필요한 근거의 핵심** — 규칙 기반이
구조적으로 못 하는 영역이라는 걸 이 예시로 바로 보여줄 수 있음.
