# 신기훈 5주차 결과물 01 - 1차 분석에 문장 규칙·상황 규칙 반영

> 5주차 팀 공통 목표: *"1차 분석이 키워드 + 문장 규칙 + 상황 규칙을 함께 반영하도록 만들기"*
> 신기훈 담당 항목: `DetectionEngine.analyze()`에 문장 규칙 점수 반영, 상황 규칙 점수 반영,
> `shouldEscalateToAI()`는 애매한 경우만 남기도록 정리.
>
> **완료 기준**: "1차 분석이 더 이상 키워드 중심만이 아니어야 함" — 이 문서가 그 증거.

---

## 0. 이번 주 전에는 어떤 상태였나

4주차 수정2 리뷰에서 지적받은 내용: *"문장/상황 기반 판단이 `shouldEscalateToAI()`(AI 호출
여부 판단)에만 있고, `DetectionEngine.analyze()`(1차 위험도 계산 본체)는 여전히 키워드
매칭/`repeat_decay`/`combo_bonus` 중심이다."*

그 지적에 대한 1차 대응(4주차 수정2, `주차별_결과물/4주차_결과물_신기훈/09번 문서`)으로
"상황 규칙"(가스라이팅 반복, 장기세션) 2개를 온디바이스 점수에 이미 반영해뒀다. 이번 주는
그 다음 단계 — ① 상황 규칙과 중복된 AI 호출 조건 정리, ② 완전히 새로운 층인 "문장 규칙"
추가.

---

## 1. shouldEscalateToAI() 정리 — 애매한 경우만 남기기

**Before (4주차까지)**: 회색지대 점수, 수동신고, 가스라이팅 반복 2회+, 장기세션 15턴+,
신규 subcategory — 5개 조건.

**After (5주차)**: 회색지대 점수, 수동신고, 신규 subcategory — 3개 조건.

가스라이팅 반복/장기세션 트리거를 제거한 이유: 4주차 수정2 대응으로 이미
`COMBO-GL-REPEAT-PATTERN`/`COMBO-RS-LONG-SESSION-PATTERN`이 온디바이스 점수에 반영돼
있어서, 똑같은 패턴을 "AI를 또 부르는 이유"로 중복 유지할 필요가 없어졌다. 이제
`shouldEscalateToAI()`는 정말로 "온디바이스 규칙만으로는 판단이 애매한 경우"(점수가
경계에 걸치거나, 사용자가 직접 위험하다고 표시하거나, 아직 신뢰도가 안 쌓인 신규
데이터)만 남는다.

부수 정리: 더 이상 쓰이지 않는 `sessionTurnCount` 파라미터도 함께 제거했다
(`DetectionEngine`/`DetectionRepository`/`DetectionViewModel` 전부 갱신). 제거된 2개
트리거의 회귀 커버리지는 `DetectionEngineTest`의 `TC-COMBO-07`/`TC-COMBO-08`(온디바이스
점수 콤보 검증)이 그대로 담당하므로 커버리지 손실은 없다.

## 2. 문장 규칙 신설 — `match_type: regex-complex`

### 2-1. 정의

기존 두 층(키워드 매칭·상황 규칙)과 구분되는 세 번째 층. **정규식만으로는 부족하고, 캡처된
숫자값 자체가 조건에 들어가야 판단 가능한 문장**을 대상으로 한다.

예: `"정 그러면 100만원만요. 그 이상은 안 돼요."` — "숫자+만원만" 패턴 자체는 regex로 잡을
수 있지만, **100만원은 위험 신호(소액한정 요구 SMALL_ASK)여도 1000만원은 오히려 "소액"이
아니라서 같은 신호로 볼 수 없다.** 이런 조건부 판단은 `keyword`/`regex-simple`로는 표현이
안 된다.

이 gap은 실은 새로운 발견이 아니라, 06번 문서(4주차)에서 이미 "regex로 대응 가능하나 이번
확장에선 의도적으로 보류"라고 명시해뒀던 항목(`신규_기법_문장_수집_v1.json` N-RS2-02,
`root_cause_category: NUMERIC_PATTERN`)이다. keyword.json의 `field_guide`에도 애초에
"regex-complex"라는 이름이 예약돼 있었다 — 이번 주에 실제로 구현했다.

### 2-2. 구현

`KeywordEntry`에 3개 필드 추가:

```
numeric_capture_group: pattern의 몇 번째 캡처그룹이 숫자인지 (기본 1)
numeric_min / numeric_max: 캡처된 숫자의 허용 범위 (둘 다 생략하면 regex-simple과 동일)
```

`matchKeywordsInTurn()`에 `"regex-complex"` 분기 추가: 정규식은 맞아도 캡처된 숫자가
범위 밖이면 매칭으로 인정하지 않는다. 그 외에는 `regex-simple`과 완전히 동일한 경로
(scoreMatches/resolveInstitutions/matchedKeywords 전부 그대로 재사용) — 새로운 인프라를
만들지 않고 기존 파이프라인에 조건 하나만 끼워 넣은 구조라 회귀 위험이 작다.

신설 키워드:

```json
{ "id": "RS-2-9-003", "match_type": "regex-complex",
  "pattern": "(\\d+)\\s?만원만", "numeric_capture_group": 1, "numeric_max": 500, "weight": 15 }
```

| 입력 | 결과 |
|---|---|
| "100만원만요" | ✅ 매칭 (RS-2-9-003, 소액 선요구) |
| "500만원만요" (경계값) | ✅ 매칭 |
| "501만원만요" (경계값 초과) | ❌ 매칭 안 됨 |
| "1000만원만요" | ❌ 매칭 안 됨 — 큰 금액이라 "소액 한정"의 취지가 아님 |

갭 코퍼스(`신규_기법_문장_수집_v1.json`, 38문장) 결과: **30/38 → 31/38**.

## 3. 스트레치: `numeric_ratio_pattern` (NUMERIC_REASONING 부분 대응)

시간이 남아 한 단계 더 진행했다. `"3주만에 100이 137 됐죠?"` — 100에서 137로, 즉 **37%
수익률이라는 걸 계산해야만** 위험 신호임을 알 수 있는 문장(06번 문서: *"키워드 매칭으로
구조적으로 거의 불가능"*).

`combo_bonus_rules`에 새 타입 `numeric_ratio_pattern` 추가 — pattern의 캡처그룹 1·2번을
"이전 값"·"이후 값"으로 보고 증가율(%)을 계산해서, `min_growth_rate_percent`(15%) 이상이면
`COMBO-RS-NUMERIC-RATIO`(+15점) 발동.

```
COMBO-RS-NUMERIC-RATIO: pattern="(\d+)\s*(?:이|가)\s*(\d+)\s*(?:됐|되었|늘었|올랐|불었)"
"100이 137 됐죠?" -> (137-100)/100*100 = 37% >= 15% -> 발동 (+15점)
"100이 105 됐죠?" -> 5% < 15% -> 미발동
"100이 90 됐어요" (감소) -> 미발동
```

**중요한 한계**: 이 규칙은 원문 전체에 정규식을 돌려 "숫자 두 개의 관계"만 보는 방식이라,
뒷받침하는 실제 키워드 매칭이 없다 — `repeat_pattern`/`long_session_pattern`과 달리 이
콤보는 `matchedKeywords`가 비어있어도 발동한다. 그래서 **점수(`appliedComboIds`)에는
반영되지만 `category`/추천기관에는 반영되지 않는다** (이 신호만으로는 어떤 institution을
추천할지 판단할 근거가 없어서). `신규_기법_문장_수집_v1.json`의 N-RS2-03은 이 코퍼스가
"keyword id 매칭 기준"이라 여전히 `known_gap`으로 남아있다 — 점수 대응은 됐지만 완전
해소는 아니라는 뜻. 완전한 해소(카테고리/기관 추천까지)는 다음 단계로 남겨둠.

## 4. 완료 기준 검증: "1차 분석이 키워드 중심만이 아니다"

같은 입력에서 세 층이 독립적으로 작동하는 걸 보여주는 예시:

```
입력: "너 오늘 좀 예민한 거 같아, 별일도 아닌데 왜 그래?
      내가 언제 그렇게 말했어? 너 또 왜곡해서 기억하는 거야."

1) 키워드 매칭: GL-3-1-001/003, GL-3-2-001/003 (weight 합산, repeat_decay 적용) = 45점
2) 상황 규칙: 가스라이팅 반복 트리거 subcategory가 세션에서 4회 매칭
   -> COMBO-GL-REPEAT-PATTERN 발동 = +15점
3) 최종: 60점 (중간) -> 75점 (높음)  [TC-GL-EDGE-01]
```

```
입력: "정 그러면 100만원만요. 그 이상은 안 돼요."

1) 키워드 매칭: 없음 (기존 키워드로는 못 잡음)
2) 문장 규칙: "(\d+)\s?만원만" + 숫자 범위(<=500) 조건부 매칭
   -> RS-2-9-003 매칭 = 15점
3) 최종: 15점, category=로맨스스캠, 추천기관 연결까지 정상 동작
```

```
입력: "3주만에 100이 137 됐죠?"

1) 키워드 매칭: 없음
2) 문장 규칙(숫자 관계): 두 숫자의 증가율 37% 계산 -> 임계값(15%) 초과
   -> COMBO-RS-NUMERIC-RATIO 발동 = +15점 (점수에만 반영, 3장 한계 참고)
```

세 예시 모두 **키워드 매칭만으로는 지금과 다른(더 낮거나 아예 0인) 결과가 나왔을 상황**을
문장 규칙/상황 규칙이 보정한다 — 완료 기준 충족.

## 6. 남은 작업 / 알아둘 것

- `numeric_ratio_pattern`은 category/추천기관까지 연결되지 않음(3장 한계) — 다음 단계에서
  가상 매칭(synthetic match) 형태로 확장할지, 아니면 지금처럼 "점수 전용 보정"으로 계속
  둘지는 팀 논의 필요
- `regex-complex`/`numeric_ratio_pattern` 둘 다 아직 1건씩만 등록됨 — 실사용 데이터가
  쌓이면 유사 패턴을 더 추가할 수 있는 구조는 마련해뒀음
- TONE_IMPLICATURE(문자 그대로는 안전해 보이나 맥락상 함의가 위험한 유형)는 이번 범위에서
  의도적으로 제외 — 이건 구조적으로 AI/회색지대가 담당해야 하는 영역이라는 06번 문서
  결론 그대로 유지
